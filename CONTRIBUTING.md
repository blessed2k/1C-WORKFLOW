# Участие в разработке

Спасибо за интерес к проекту. Перед крупным изменением откройте issue и опишите задачу:
так проще договориться о подходе до написания кода.

## Сборка и тесты

Нужен Go 1.26 или новее.

```sh
go build ./...
go vet ./...
go test ./...
```

Перед pull request прогоните `go vet` и `go test ./...` (при изменениях конкурентного кода
также `go test -race ./...`) и проверьте кросс-сборку, если трогали платформенный код:
`CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./...`. Тесты на реальных выгрузках
включаются переменными окружения, их список в README.

## Правила кода

- **Границы пакетов проверяются тестами.** `internal/arch` содержит гард на граф импортов:
  `internal/domain` зависит только от стандартной библиотеки, SQL живёт только в
  `internal/store`, `cmd/mcp1c` ходит в индекс через `internal/app`, новый код не
  импортирует слой `internal/source`. Если гард покраснел, исправляйте зависимость, а не
  список исключений.
- `CGO_ENABLED=0` всегда; платформенный код выносится в файлы с build-тегами и одинаковой
  сигнатурой.
- Контрактные тесты инструментов (`cmd/mcp1c/tools_contract_test.go`,
  `tools_behaviour_contract_test.go`) защищают формат ответов: менять контракт существующего
  инструмента нельзя, новое необязательное поле допустимо.
- Новый индексный инструмент добавляется своим файлом `cmd/mcp1c/idx_<имя>.go` с `init()`.
- Описание инструмента должно говорить, когда его вызывать.
- Изменили выход парсера: поднимите `index.ParserVersion`.
- Тесты табличные и приходят в том же коммите, что и код. Пути в фикстурах выгрузки строятся
  помощниками `workspace.Dump*`.
- Форматирование `gofmt` для изменённых файлов. Язык комментариев такой же, как у соседнего
  кода; тексты для пользователя (сообщения в ответах и stderr) на русском.
- Имена объектов 1С в фикстурах вымышленные.
- Не коммитьте учётные данные, выгрузки чужих баз, индекс синтаксиса платформы и каталог
  `.mcp1c/`.

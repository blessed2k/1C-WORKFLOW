# Архитектура: единый сервер, ресурсная модель и объектный граф (visualization)

Статус: ACCEPTED. Факты проверены по коду на ветке `feat/indexed-mcp` (HEAD
`45a7a1a`) на момент принятия. Точный DDL и API: результат фазы реализации, здесь
контракты и инварианты. Метки D1-D14 определены в разделе 3.

Связанные документы: `architecture-index.md` (индекс, epoch/generation, derive).

---

## 1. Цель и рамки

Три работы одним связным планом:

1. **Единый сервер.** Убрать двойную регистрацию сервера (обычная + индексная
   запись в конфиге клиента): это одна кодовая база в двух срезах времени
   (main от 27.07 и feat/indexed-mcp от 20.08), а не два продукта.
2. **Ресурсная модель.** Долгоживущий MCP-процесс не должен держать оперативу
   в простое (на рабочих машинах процессы копятся и грузят RAM).
3. **Объектный граф.** Визуализация для человека (разработчика): транзитивный радиус
   документа (регистры, документы, HTTP-переходы между базами), god-node
   аналитика, позже raw/effective diff. Плюс один компактный MCP-инструмент
   той же природы для агента.

Не в рамках: изменение протокола MCP, переезд raw-инструментов на индекс
(решение D11: сейчас это направление НЕ выбрано), визуальный дизайн UI (здесь
только принцип).

## 2. Контекст: проверенные факты (20.08.2026)

- Регистрации в конфиге клиента: `mcp1c --dump <выгрузка>` (бинарник от
  27.07, main) и `mcp1c-indexed` без `--dump` (от 20.08, feat/indexed-mcp).
  Indexed-бинарник содержит ВСЕ базовые инструменты плюс индексные.
  Ошибка `no configuration source` у не-indexed сервера в реальной сессии:
  следствие конфигурации запуска (нет источника), не архитектуры.
- На машине разработки в момент проверки 7 живых процессов (5 × mcp1c, 2 × mcp1c-indexed,
  старты 8:44...9:14): множитель «сессии × 2 сервера» плюс возможные сироты.
- `cmd/mcp1c/main.go`: `ss.Wait()` корректно завершает процесс по EOF/разрыву
  stdio. Сам сервер сирот не порождает; копление процессов идёт от клиента
  (много окон, грязные падения) и от двойной регистрации.
- `internal/source/cache.go`: процесс-wide кэш разобранных коллекций выгрузки
  БЕЗ вытеснения и БЕЗ потолка памяти, живёт до конца процесса. На больших
  базах это главный вклад в «висит и держит оперативу».
- `register_access` (SQL: file_id, symbol_id, object_id, register_name_norm,
  mode, in_transaction, static, confidence, byte_start, byte_end) НЕ хранит
  `layer`; `dependency_edge` хранит. Raw/effective протянут по индексу
  неравномерно (см. также architecture-index.md).
- `register_access.object_id` = регистр, не владелец. Владелец восстанавливается
  цепочкой symbol_id → метод → модуль → объект-владелец; цепочка до конца не
  доказана (проверка = первая задача В1).
- На машине разработки есть только `ut_demo` (УТ 11.5.22), выгрузок с расширениями
  и отраслевых конфигураций нет. Калибровка на ut_demo, боевое применение на других
  конфигурациях.
- В ut_demo нет расширений: проверка `layer` только на синтетической фикстуре
  (паттерн mutation-теста DeriveIntercepts уже есть в репо).

## 4. Топология: единый сервер

Целевое состояние: `feat/indexed-mcp` смержена, один бинарник `mcp1c`, одна
запись в конфиге клиента. Старый бинарник и вторая регистрация удаляются. Выигрыш: минус дубль
30+ схем инструментов в контексте каждой сессии, минус один Go-процесс на
каждую сессию у каждого пользователя.

### 4.1. Единый активный проект (D2)

Одна карта состояний сервера: `проект → {корень выгрузки, live-база (опц.),
индекс (есть/нет, свежесть)}`.

- `set_dump <путь>` активирует проект для обоих слоёв. Если под корнем уже
  есть индекс (`.mcp1c/`), индексные инструменты работают по нему сразу.
- Вызов индексного инструмента при единственном проиндексированном проекте
  делает его активным и для raw-слоя.
- Индексный инструмент без индекса: ошибка с точной командой (`reindex
  projectRoot=...`). Автоиндексация запрещена: первый вызов не имеет права
  молча жечь минуты и гигабайты на 2 ГБ выгрузке.
- `server_info` показывает всю карту: активный проект, источники, статус
  индекса, а после D14 ещё и память (см. раздел 6).

### 4.2. Мульти-база (D3)

Обмены делают работу с двумя базами одновременной нормой. Модель:

- один активный проект по умолчанию (как сейчас);
- ЛЮБОЙ инструмент принимает `project=` (offline) / `base=` (live) как
  разовый override без переключения глобального состояния;
- кросс-базовые инструменты (exchange_audit, будущий graph, В2-сшивка)
  принимают список проектов явно;
- live остаётся измерением проекта, не отдельной сущностью.

## 5. Ресурсная модель процесса (D14)

Констатация протокола: exe запускает и гасит клиент (Claude Code), по процессу
на сервер на сессию. Агент процессами не управляет. Перезапуск на каждый вызов
означал бы повторный парсинг выгрузки на каждый вызов (секунды и хуже) и
отвергнут.

Меры (все внутри существующего процесса):

1. **Idle-TTL кэша выгрузки.** `exportCache` получает время последнего
   обращения на запись; фоновый тикер сбрасывает записи, к которым не
   обращались N минут (tunable, старт 10 мин). Следующий вызов перечитывает
   как при холодном старте: заметно, но честно.
2. **Потолок кэша.** Оценочный размер записей суммируется; при превышении
   потолка (tunable) вытесняется давнее. Потолок и TTL едины для всех
   проектов процесса.
3. **Ленивые загрузки.** Тяжёлые статические структуры (корпус bsl_syntax
   ~23k записей и подобное) грузятся по первому обращению, не при старте.
4. **Наблюдаемость.** `server_info` отдаёт RSS процесса, состав кэша
   (проект, коллекции, оценка размера, возраст) и аптайм. Без этого спор
   «кто съел память» опять пойдёт по скриншотам диспетчера задач.
5. **Гигиена процессов.** Код завершения по EOF уже корректен. На рабочей
   машине: разовый аудит (сопоставить живые mcp1c.exe с живыми сессиями),
   и после D1 множитель процессов падает вдвое сам.

НЕ делаем: spawn-per-call, самовольный exit по таймеру (клиент считает сервер
живым и получит разрыв), общий демон на всех пользователей.

## 6. Объектный граф: модель данных

### 6.1. Узлы

Объекты метаданных (документы, регистры, справочники, обработки, HTTP-сервисы
и т.д.) из существующей identity-модели индекса. Модули и символы узлами карты
НЕ являются (D6): они схлопываются в атрибуцию и evidence.

### 6.2. Таблица `object_data_edge` (D8, эскиз контракта)

Производная таблица индекса, строится на derive/publish, инкрементально
пересчитывается по той же модели зависимостей, что остальное производное
(resolution_dep). Поля (имена уточняются в storage-фазе):

- `from_object_id`, `to_object_id`: узлы;
- `kind`: `writes-register` | `reads-register` | `reads-query` |
  `ref-attribute` | `creates` | `http-call` (В2);
- `layer`: base | имя расширения (D11, с первого дня);
- `confidence`: минимум по цепочке атрибуции, типизированный (эвристика не
  может выдать себя за 1.0, инвариант индекса сохраняется);
- `evidence`: компактная ссылка на цепочку (символы пути атрибуции,
  file_id/byte-диапазоны конечного факта): для «показать почему» в UI и
  для отладки атрибуции;
- служебные: mode/in_transaction для регистровых рёбер (переносятся из
  register_access).

Той же миграцией `register_access` получает `layer` (данные у парсера есть,
один пересбор индекса, вторая миграция не понадобится).

### 6.3. Атрибуция (D6, D7)

Запись в регистр, сделанная в общем модуле, приписывается объекту-владельцу
вызывающей цепочки: register_access.symbol → вверх по СТАТИЧЕСКОМУ call graph
до символов, чьи модули принадлежат объектам (модуль объекта, менеджера,
формы). Правила:

- только статические разрешённые вызовы; `confidence` ребра = минимум по
  цепочке;
- регистр должен быть резолвлен статически (`static`, известный object_id);
- динамика (`Выполнить`, имя регистра из параметра, менеджер по строке) рёбер
  НЕ порождает, но объект получает бейдж `has-dynamic` со счётчиком: дыра
  видима, а не замалчивается;
- один и тот же факт, достижимый несколькими цепочками, даёт одно ребро с
  максимальным из confidence цепочек, evidence хранит кратчайшую;
- защита от хабов: пороги (глубина цепочки, fan-in промежуточной процедуры)
  выражаются в confidence, а не отрезают рёбра молча. Все пороги: tunables,
  калибровка на ut_demo, не константы в коде.

Известный риск: качество атрибуции на БСП-хабах (`ПроведениеСервер` и родня).
Проверяется первой задачей В1 (раздел 10).

## 7. Пайплайн

```
parse (facts)                resolve/derive                publish
─────────────                ──────────────                ───────
register_access(+layer)  →   DeriveObjectDataEdges:    →   object_data_edge
call graph (есть)            свёртка symbol→module→        (+ индексы по from,
query facts (есть)           owner, атрибуция, min-        to, kind, layer)
ref facts (есть)             confidence, evidence
http_call facts (В2)     →   сшивка по пути (В2)       →   http-рёбра (В2)
http_endpoint facts (В2)
```

Потребители `object_data_edge`:

1. **graph-режим** (HTTP API для SPA);
2. **MCP-инструмент `object_graph`** (агенту);
3. будущие инструменты (никого не заставляем повторять BFS по символам).

## 8. Graph-режим (D4, D12, D13)

- Запуск: `mcp1c graph --project <корень> [--project <корень2> ...] [--listen
  127.0.0.1:0]`. Отдельный процесс, живёт до Ctrl+C, слушает только localhost.
  Печатает URL и открывает браузер (флагом отключаемо).
- Читает те же SQLite-файлы индекса в WAL read-транзакциях: MCP-процессу не
  мешает; при смене эпохи (rebuild) переоткрывает по указателю эпохи.
- Индекса нет: та же честная ошибка, что D2 («запусти reindex»).
- SPA: один HTML + vendored cytoscape.js, вшито go:embed. Node-тулчейна в
  репо не появляется.

### 8.1. HTTP API (контракт, пути уточняются)

- `GET /api/projects`: подключённые проекты и свежесть индексов;
- `GET /api/node/{id}`: карточка объекта (тип, имя, бейджи, счётчики);
- `GET /api/neighbors/{id}?dir=in|out|both&kinds=...&minConfidence=...&layer=...`:
  соседи для раскрытия по клику; ответ страничный, с `total`;
- `GET /api/radius/{id}?depth=N&...`: транзитивный радиус с теми же фильтрами
  и жёстким потолком узлов (tunable; при превышении режется по confidence и
  сообщает об этом явно, никаких молчаливых обрезаний);
- `GET /api/godnodes?metric=fan-in|fan-out&type=...&top=N`: аналитика
  перегруженных узлов;
- `GET /api/edge/{id}/evidence`: цепочка «почему ребро существует»;
- В2: `GET /api/crosslinks?projects=...`: HTTP-рёбра между проектами.

Progressive disclosure живёт на этом API: UI не грузит весь граф никогда.

## 9. MCP-инструмент `object_graph` (D9)

Один инструмент, тонкая обёртка над той же таблицей: параметры `object`,
`direction`, `kinds`, `depth` (потолок маленький, 1-2), `minConfidence`,
`project=`, бюджет размера ответа как у остальных индексных инструментов.
Отдаёт объектную картину одним дешёвым вызовом вместо серии символьных
(find_register_writes + find_references + ручная свёртка). Не заменяет
символьные инструменты: это другой уровень зума.

## 10. Веха В1: карта + god-node (одна база)

Состав: миграция схемы (layer в register_access, object_data_edge),
DeriveObjectDataEdges, graph-режим с API из раздела 8, `object_graph`,
калибровка на ut_demo.

Порядок с проверками:

1. **Доказательство цепочки владельца** (риск №1): на ut_demo вручную
   проверить для 3-5 документов, что symbol → модуль → владелец даёт то же,
   что `find_register_writes` + чтение кода. Если цепочка не собирается,
   остановка и пересмотр (данных в индексе не хватает: это меняет объём).
2. Миграция схемы + derive, go-тесты на атрибуцию: прямая запись, запись
   через общий модуль, хаб с параметром-регистром (не даёт ребра, даёт бейдж),
   цикл в call graph (терминируется), min-confidence.
3. Синтетическая фикстура с расширением: заполнение layer доказано
   mutation-тестом (в ut_demo расширений нет).
4. graph-режим + SPA.
5. Замер бюджетов: размер индекса и время reindex на ut_demo до/после
   (известный долг памяти ~4x не усугубляем; числа в benchmarks.md).

Критерий готовности: на ut_demo открыть документ, увидеть транзитивный радиус
с раскрытием по клику и фильтром confidence; топ god-node по регистрам
совпадает с ручной проверкой через find_register_writes; derive покрыт тестами.

## 11. Веха В2: кросс-базовые HTTP-рёбра (D10)

- **Факты на стороне вызывающего:** parse собирает исходящие HTTP-вызовы с
  URL-литералами (константы, конкатенации со статической базовой частью;
  динамические URL честно помечаются неразрешёнными).
- **Факты на стороне принимающего:** HTTP-сервисы из метаданных (RootURL,
  шаблоны, методы) — уже знакомая индексу структура.
- **Сшивка:** по совпадению пути (RootURL + шаблон с параметрами); хост
  резолвится конфигом воркспейса `{паттерн хоста → проект}` (маленький файл
  рядом с индексами; формат в фазе реализации). В обследованных базах URL захардкожены в
  коде, поэтому сопоставление надёжное, не гадание.
- **Несовпавшие вызовы не теряются:** узел «внешний HTTP, адресат неизвестен»
  на карте: сам по себе полезный сигнал про дыры.
- Кросс-проектный join выполняет graph-режим (и `object_graph` при явном
  списке проектов), индексы баз остаются независимыми файлами.

Критерий готовности: синтетическая двух-проектная фикстура (сервис + вызов),
ребро строится, немапленный хост даёт «внешний HTTP»; на рабочих базах
ручная проверка по известной паре обменов.

## 12. Веха В3: raw vs effective diff

Данные уже лежат с В1 (layer в рёбрах). Остаётся UI-режим: два состояния карты
(«как декларирует база» / «как действует с расширениями») и подсветка дельты.
Для конфигурации с расширениями осмысленно, для конфигурации с доработками прямо в
типовом коде неприменимо физически (нет разделения база/расширение) — такая карта
всегда «как есть», режим просто недоступен.

Смежный известный долг (raw/effective в get_context_for_task для
register/query/rights/posting) в эту веху НЕ входит: отдельная задача, но
колонка layer из В1 ей уже пригодится.

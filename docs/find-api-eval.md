# Оценка find_api: эталон «задача словами → готовый метод»

Набор отвечает на один вопрос: находит ли `find_api` готовый метод, когда разработчик
описывает задачу своими словами. Им меряется каждое изменение поиска; число, полученное
на трёх десятках запросов, придуманных тем же, кто пишет правила, оценкой не считается.

Набор: `evals/findapi/data/ut_demo.jsonl` (УТ 11.5.22, БСП 3.1.11.366), 498 пар.
Программа: `evals/findapi` (не production-код, MCP-инструментом не является).

## Как построена пара

1. **Источник: настоящий вызов.** Берётся метод программного интерфейса (тот же отбор, что
   у `find_api`: `APIService.Catalog`) и место, где его зовут из другого модуля
   (`find_references`, вид `call`, без неоднозначно разрешённых ссылок).
2. **Имя скрыто.** Из модуля вырезается вызывающая процедура (длинная режется до окна
   вокруг вызова), и имя метода вместе с модулем, через который он позван, заменяется на
   `ИскомыйМетод`: в вызове, в комментарии, в строке, в имени соседнего метода, если оно
   надстроено над искомым. Фрагмент отвергается, когда имя вызывающей процедуры само выдаёт
   метод (обёртка, имя-надстройка, две трети тех же слов).
3. **Запрос пишет модель, не видя метода.** Задание: «этот код пишешь ты, готового метода
   под рукой нет; напиши, что ты искал бы в каталоге методов». Модель вправе ответить «по
   фрагменту не понять». Вторым полем она пишет **пересказ**: тот же запрос словами другого
   разработчика 1С. Термины платформы и предметной области в пересказе остаются, меняются
   глаголы, построение фразы и общие слова.
4. **Пару проверяют две модели независимо.** Каждая видит запрос, вызов, сигнатуру и полный
   комментарий метода и принимает пару, только если метод делает именно то, что описано, а
   запрос достаточно конкретен. В набор идёт пара, принятая обеими. Проверяющие разного
   класса (Sonnet и Opus), их вердикты совпали на 86% пар. Запрос, назвавший метод его
   идентификатором, отбрасывается до проверки.
5. **Засчитываются равноценные ответы.** Ответом считается сам метод, метод с тем же именем
   в модуле того же семейства (`ОбщегоНазначения` и `ОбщегоНазначенияКлиент`) и одноимённый
   метод другой секции (прикладной метод с тем же именем, что у метода библиотеки). Сверку
   таких тёзок проверяющие модели не делали: они видели только сам метод. Метод ищется в
   обеих секциях ответа: агент читает обе.

Тексты заданий обеим моделям лежат константами в `evals/findapi/main.go`.

## Выборка

Детерминированная: порядок задаёт зерно и идентификатор метода, повторный запуск на той же
выгрузке даёт тот же файл задач байт в байт. Идентификатор задачи выводится из метода и
места вызова, идентификатор пары на проверке ещё и из текста запроса: ответ модели на
задачу прежнего запуска и вердикт по прежней редакции запроса к новым не приклеятся.

- В каталоге 3035 методов библиотеки (2823 действующих) и 21540 прикладных (21331).
- Не берутся устаревшие методы и методы с именем, которое носят три семейства модулей и
  больше (506 имён вроде `ДобавитьКомандыПечати`): запрос, написанный по одному вызову,
  такие методы не различает. Остаётся 2315 методов библиотеки и 13242 прикладных.
- Библиотека (секция `bsp`): 100 самых вызываемых методов (слой `core`) и 200 случайных из
  остальных, у которых есть вызов из другого модуля (слой `rest`). У 31 метода ни одно
  место вызова не дало годного фрагмента.
- Конфигурация (секция `other`): 250 случайных методов с вызовом из другого модуля
  (просмотрено 410).
- Из одного семейства и из одноимённых методов берётся один.

## Что меряется

Доля запросов, на которые засчитанный метод стоит в первых 1, 3, 10, 20 и 50 секции.

- Первые 1, 3, 10 и 20 считаются по выдаче `find_api` без `limit`: десять полных описаний
  и короткий список из следующих десяти. Двадцатка главная: это то, что агент видит на
  самом деле, а читает выдачу модель, не человек.
- Первые 50 считаются по выдаче с `limit=50`: потолок инструмента.

Это два разных вызова, а не срез одного: `find_api` уводит устаревшие методы в хвост уже
после среза, и место в длинной выдаче не равно месту в короткой.

Группы: секция, половина, вид запроса, слой выборки и признак «у запроса есть общие слова
с именем метода». Признак считается своим разбором слов, не ранжировщиком `find_api`:
иначе он менялся бы вместе с правилами, которые по нему меряются.

## База

Замер 04.10.2026 текущим кодом. «Видит агент» значит «метод есть в выдаче без `limit`»:
десять полных описаний и короткий список из десяти.

Половины набора неравны по трудности: проверочная легче настроечной при любом поиске (так
легло деление по семейству метода). Поэтому числа даны по обеим половинам и по всему набору;
число по одной проверочной половине завышает качество. В половине `test` 261 пара на 152
метода, в `dev` 237 пар на 126 методов: прямой запрос и пересказ одного метода зависимы, и
интервал ниже (95%, по Уилсону, как для независимых пар) на деле шире.

- «До»: поиск по имени метода, имени модуля и первой строке описания, выдача из десяти
  методов (коммит `d13e741`, замер тем же набором в отдельном рабочем каталоге индекса).
- «После»: поиск ещё и по полному комментарию с весом поля, две редкости слова, точность
  имени, короткий список следующих десяти методов. Правила подобраны по настроечной
  половине.

Медиана вызова при запросах по одному (`-jobs 1`): 5 мс без карточек, 7 мс с карточками. До
изменения было около 300 мс (294 и 431 мс в двух прогонах): слова методов теперь разбираются
один раз на поколение индекса, а не на каждый вызов. Базы лежат в
`evals/findapi/data/ut_demo.baseline.json` и `ut_demo.cards.baseline.json`, полная таблица
печатается прогоном.

Что остаётся ненайденным без карточек, видно на настроечной половине: «оставить в массиве
только уникальные элементы» против `СвернутьМассив`, «вычесть один массив из другого» против
`РазностьМассивов`, «вставить значения параметров в шаблонную строку» против
`ПодставитьПараметрыВСтроку`. Это синонимы, которых нет ни в имени, ни в комментарии
метода; поиск по словам имени и комментария их не возьмёт.

Запросы, не принятые проверкой как неточные или общие (161, в набор не входят), поиск
берёт заметно хуже: агент видит метод у 83% таких запросов по библиотеке и 72% по
конфигурации против 98% и 96% у принятых прямых (по всему набору, замер 03.10.2026). Из 440
понятных прямых запросов в набор вошло 259: число «по всем написанным запросам» ниже, чем
94% по набору.

Счёт засчитывает не только сам метод (см. «Как построена пара», пункт 5). По разбору
исходов без карточек из 399 попаданий в первую пятёрку 381 это сам метод, 14 его близнец
по семейству модулей, 4 одноимённый метод другой секции. На глубинах 10, 20 и 50 это счёт
не меняет, первое место завышает на единицы пар.

## Карточки задач

Карточка метода: формулировки задачи словами разработчика (как правило от трёх до пяти) и
строка «вместо какого самописного кода метод зовут». Пишет её языковая модель по сигнатуре и
комментарию метода (`cmd/apicards`), один раз на версию библиотеки или конфигурации;
`find_api` ищет по карточке наравне с именем и комментарием. Наборы для `ut_demo`:
`bsp-3.1.11.366` (2821 карточка на 2823 действующих метода библиотеки) и `ut-11.5.22`
(21 331 прикладной метод). У методов без описания (обработчики событий, служебные методы)
формулировок одна или две: так у 148 карточек библиотеки и у 332 прикладных.

**В репозиторий наборы не входят.** Сервер без сгенерированных карточек работает по строке
«без карточек»; числа «с карточками» описывают сервер, рядом с которым лежат именно эти два
файла.

Замер 04.10.2026, весь набор и половины:

| Со всеми карточками против поиска без них | `dev`, 237 | `test`, 261 | Весь набор, 498 | Приобретено / потеряно (весь набор) |
|---|---|---|---|---|
| Метод стоит первым в своей секции | 124 → 148 (62%) | 131 → 175 (67%) | 255 → 323 (65%, 61..69) | 98 / 30 |
| В первых 10 (полные описания) | 204 → 226 (95%) | 235 → 246 (94%) | 439 → 472 (95%, 92..96) | 41 / 8 |
| Видит агент (первые 20) | 217 → 233 (98%) | 251 → 253 (97%) | 468 → 486 (98%, 96..99) | 22 / 4 |
| В первых 50 | 229 → 236 (100%) | 255 → 259 (99%) | 484 → 495 (99%) | 12 / 1 |

Как это читать.

- По главной глубине (видит ли агент метод) карточки дают 18 пар из 498: с 94% до 98%. На
  проверочной половине это 2 пары (потолок там почти достигнут и без карточек), на
  настроечной 16. Разница 96% и 97% на одной половине ничего не значит.
- Заметнее карточки двигают метод к началу списка: первым в своей секции он стоит у 65% пар
  против 51%. «Первым в секции» не значит «первой строкой ответа»: секций две, и первый
  прикладной метод стоит после двадцати строк библиотеки. Что агент чаще берёт первый метод
  секции и не дочитывает выдачу, здесь не мерялось: это допущение.
- Карточки не только поднимают, но и роняют: первое место потеряли 30 пар (приобрели 98), из
  выдачи без `limit` выпали 4 (вошли 22). Метод, поднятый чужой формулировкой, агент по
  ответу не проверит: текст карточки в ответ не попадает, виден только сам метод с его
  описанием.
- Только карточки библиотеки (без прикладных), проверочная половина: первое место 163,
  первые 10: 244, первые 20: 251, первые 50: 256 (замер 04.10.2026, в базе не хранится).

Вес поля карточки в охвате 0,7 подобран по настроечной половине (`score -split dev`, все
карточки; первое место, первые 10 и первые 20):

| Вес | `bsp/dev`, 154 | `other/dev`, 83 |
|---|---|---|
| 0,4 | 93, 141, 147 | 49, 77, 82 |
| 0,55 | 93, 143, 149 | 47, 78, 82 |
| **0,7** | **93, 148, 150** | **55, 78, 83** |
| 0,85 | 85, 147, 150 | 55, 80, 83 |
| 1,0 | 82, 143, 150 | 55, 80, 82 |

Три синонима из раздела «База» с карточками: `РазностьМассивов` на первом месте,
`ПодставитьПараметрыВСтроку` на третьем, `СвернутьМассив` на шестнадцатом (в коротком
списке). Это иллюстрация, а не свидетельство: все три пары из настроечной половины, а пример
в задании модели, писавшей карточки, был взят как раз с `СвернутьМассив` (в коде задания он
заменён, наборы собраны с прежним).

Чего этот замер не доказывает.

- **Запросы эталона и карточки писала одна и та же модель** (Claude Sonnet): запросы по коду
  места вызова, карточки по описанию метода, друг друга исполнители не видели. Словарь
  модели в запросах и в карточках общий, и на запросах живого разработчика прирост может
  быть меньше. Проверки на запросах другого происхождения нет.
- Дословно с запросом эталона совпали 3 формулировки карточек из 498 пар, близких (общие
  основы слов не меньше 0,8 по Жаккару) 15: это пересказы имени метода, не копии. Но
  технической изоляции не было: исполнители карточек работали в каталоге репозитория, где
  лежит набор эталона; для карточек библиотеки запрета открывать другие файлы в задании не
  было вовсе (теперь он в тексте задания).
- Карточки лексически ближе к запросам проверочной половины, чем настроечной (доля близких
  12 из 261 против 3 из 237). Причина не установлена; настройкой веса такого не получить.
  Это ещё один довод не опираться на одну половину.
- Качество самих карточек человек не проверял.

База с карточками лежит отдельно (`evals/findapi/data/ut_demo.cards.baseline.json`) и
воспроизводится только с теми же файлами наборов: в базе записаны имя набора и отпечаток
его содержимого, и прогон с другими карточками (в том числе пересобранными заново под тем
же именем) сравнение с ней отказывает. Прогон, которому задан каталог карточек, а поиск их
не прочитал или не привязал ни одной, останавливается ошибкой. У базы с карточками
сравнивается и первое место (допуск 3 пары на группу): иначе потеря единственного заметного
эффекта карточек прошла бы как «не ниже базы».

## Команды

Из корня репозитория. Каталог проекта: флаг `-project` или `ONEC_DUMP`.

```
go run ./evals/findapi score -project <выгрузка> -data evals/findapi/data/ut_demo.jsonl \
    -baseline evals/findapi/data/ut_demo.baseline.json
go run ./evals/findapi score -project <выгрузка> -data evals/findapi/data/ut_demo.jsonl \
    -cards <каталог карточек> -baseline evals/findapi/data/ut_demo.cards.baseline.json
```

Без флага `-cards` поиск идёт без карточек, что бы ни лежало в каталоге сервера: прогон не
зависит от настроек пользователя. `-cards server` берёт каталог сервера.

Прогон печатает таблицу и строку `НЕ НИЖЕ БАЗЫ`; при падении на глубине 10, 20 или 50 в
любой половине секции завершается ошибкой и называет группу. База привязана к набору и к
выгрузке (версия библиотеки и число методов каталога) и к наборам карточек: на другом
наборе, другой выгрузке или с другими карточками сравнение отказывает. Улучшение фиксируется флагом `-write-baseline`; вместе с
`-baseline` новая база пишется, только если прогон не ниже прежней. Флаг `-out` пишет
исход каждого запроса с первыми методами выдачи. Выдачу на один запрос печатает
`go run ./evals/findapi query -project <выгрузка> разбить строку по разделителю` (флаг `-cards`
тот же).

Храповик сравнивает обе половины, включая проверочную: это страховка от регрессии. Правила
подбираются по половине `dev` прогоном с флагом `-split dev` (он проверочную половину не
считает и не печатает, с базой не сравнивается); кто подбирает их, глядя на `test`, оценки
не имеет. Оговорка: храповик отвергает правило, уронившее `test`, то есть в отборе правил
проверочная половина всё же участвует, как запрет.

Первый запуск строит свой индекс выгрузки (минуты) в каталоге кэша пользователя,
`mcp1c-evals`, отдельно от рабочего каталога сервера; следующие открывают его как есть.
После правки выгрузки и после смены схемы индекса нужен флаг `-reindex` (полная
пересборка). Каталог общий для всех версий кода: чтобы сравнить «до» и «после», версии с
разной схемой индекса запускают с разным `-workspace`, иначе каждая будет пересобирать
индекс под себя.

Построение набора заново (другая выгрузка, другая версия БСП): шаги `tasks`, `judge`,
`assemble`, `check` описаны в начале `evals/findapi/main.go`. Рабочий каталог
`evals/findapi/work` содержит код конфигурации и в git не идёт. Тест `TestShippedDataset`
сверяет набор в репозитории с его сведениями (`meta.json`) и с отпечатком в обеих базах.

## Ограничения

- **Запрос повторяет слова имени метода.** Разработчик называет переменную по имени метода
  (`ИмяБазовогоТипа = ИскомыйМетод(...)`), и модель, читая код, пишет теми же словами. У 92
  из 169 прямых запросов библиотеки в запросе есть все слова имени метода, общие слова
  есть почти у всех. Агент, который пишет код с нуля, таких подсказок не имеет.
- **Чистых синонимов в наборе почти нет.** Пересказ сохраняет термины, поэтому запросов
  без единого общего слова с именем метода 5 из 498. Случай «информация об организации»
  против `СведенияОЮрФизЛице` этот набор не меряет; два таких запроса закреплены вручную в
  `TestRealDumpFindAPI`.
- **Набор легче настоящих запросов:** расплывчатые запросы отсеяны проверкой (см. «База»).
- **Запрос написан по коду, где метод уже вызван.** Задача в нём уже разрезана до размера
  одного метода. Агент с задачей уровня постановки («добавить проверку ИНН в документ»)
  такую формулировку сам не получит: ему ещё надо догадаться, что здесь есть что искать.
- **Отрицательных случаев нет.** Поиск всегда отдаёт до сорока строк, и набор не меряет,
  как часто агент примет за готовый метод то, что задачу не решает, когда готового метода
  нет вовсе.
- **Рамка выборки смещена в лёгкую сторону.** Не берутся методы с именем, которое носят три
  семейства модулей и больше (508 из 2823 действующих методов библиотеки, 8089 из 21 331
  прикладных), и методы, которые никто не зовёт из чужого модуля. Про них набор не говорит
  ничего.
- **Запросы писала Claude Sonnet,** проверяли Sonnet и Opus. Все модели одного производителя.
- **Один запрос и один пересказ на метод.** Разброс от формулировки меряется только парой
  «прямой запрос и пересказ».
- **Слепота пишущей модели держится на тексте задания.** Файл с ответами лежит в том же
  рабочем каталоге; технической изоляции нет.
- **Проверки человеком набор не проходил.**
  Два идентификатора в ответах проверяющей модели были записаны с опечаткой и исправлены
  по месту в пачке.
- **Одна конфигурация.** Набор привязан к выгрузке `ut_demo`; на другой выгрузке счётчик
  остановится на первом методе, которого нет в каталоге.
- **Число вызовов метода ограничено** двумя тысячами мест (десять страниц
  `find_references`): слой `core` это «очень ходовые», а не точный рейтинг, а место вызова
  у самых ходовых берётся из начала списка ссылок.
- **Набор меряет только поиск.** Спросил ли агент вообще и верно ли воспользовался
  найденным, он не знает.

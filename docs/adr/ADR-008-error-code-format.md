# ADR-8. Код ошибки — текст в фиксированной позиции, не JSON-поле (D05)

## Контекст

Спецификация (R60) требовала структурированные ответы и actionable errors —
машиночитаемый код ошибки как отдельное поле, наравне со структурными
успешными ответами (`structuredContent` по `outputSchema`).

## Решение

Таск 10 обнаружил, что `go-sdk@v1.6.1` маршалит `Out` в `structuredContent`
только на success-пути: `toolForErr`/`SetError` строят `CallToolResult` из
текста ошибки, структурного поля там нет. Ошибка отдаётся текстом
фиксированного формата `[code] message (подсказка: hint) [проект,
generation]` — агент выделяет код текстовым разбором начала строки, не
JSON-парсингом.

## Почему

Форкать или обходить `go-sdk`, чтобы протащить структурное поле `code` даже
в error-путь, не рассматривалось как соразмерное ограничению одной
библиотеки — это добавило бы второй, самодельный протокольный путь поверх
официального SDK, тот же класс риска, что и второй парсер в D01. Важно, что
это ограничение уже действовало для всех 43 существующих инструментов до
этого таска — не новый дефект таска 10, а факт, впервые ставший видимым,
когда спецификация впервые явно потребовала машиночитаемый код.

## Последствия

Код ошибки — текст в фиксированной позиции, а не JSON-поле; принято как
ограничение SDK и задокументировано один раз, чтобы таски 11–15 не решали
этот вопрос заново. Апгрейд `go-sdk`, если он когда-нибудь даст структурные
ошибки на error-пути, потребует пересмотра формата и, вероятно, изменит
контракт для клиентов, уже научившихся парсить текст по этой схеме.

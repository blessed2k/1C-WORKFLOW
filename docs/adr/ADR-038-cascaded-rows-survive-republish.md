# ADR-38. Каскадные строки нетронутых файлов переживают переопубликование владельца

## Контекст

Issue #11. ADR-037 вернул мягкие указатели (`ON DELETE SET NULL`) строк
нетронутых файлов на узлы переопубликуемого файла и назвал своей границей
второй класс: строки, которые держатся за строку-владельца не указателем, а
`ON DELETE CASCADE`. Переопубликование удаляет владельца, каскад сносит такие
строки, а их файлы в дельту не попадают, и возвращать строки некому. Индекс при
этом считает себя свежим.

Построчный тест инкремента против чистой пересборки
(`TestIncrementEqualsCleanRebuildRows`) нашёл три проявления:

- правка XML роли удаляет строку `role` (её `file_id` это XML роли), каскад
  `role_right.role_id` сносит права из нетронутого `Rights.xml`: `rights_audit`
  и права по роли пустые до полной пересборки;
- правка XML регистра удаляет `metadata_object`, каскад
  `object_data_edge.to_object_id` сносит кодовые и декларированные рёбра
  документов: зависимости рёбер (`object_data_edge_dep`) называют файлы
  цепочки и XML документа, а не XML регистра, поэтому ребро никто не
  пересобирает и признака `attribution-stale` нет;
- правка XML документа (сценарий добавлен этим решением) по той же причине
  сносит его кодовые рёбра (`from_object_id`: они зависят от модулей, а не от
  XML) и бейджи `object_badge` (у бейджа файла нет вовсе).

Попутно тест показал расхождение самой чистой пересборки: `role.object_id`
заполняет публикация XML роли, а публикация `Rights.xml`, идущая позже в той
же транзакции, перезаписывала его пустым через `EnsureRole`. Инкремент по XML
роли без `Rights.xml` оставлял указатель заполненным, и две сборки одного дерева
расходились.

## Решение

**Строка нетронутого файла, которую каскад снёс вместе с владельцем, чья
identity не изменилась, возвращается той же публикацией.** Механизм тот же, что
у ADR-037, внутри того же `WriteTx.ReplaceSourceFiles`, без смены схемы и без
переопубликации лишних файлов:

1. снимок входящих указателей (ADR-037);
2. снимок каскадных строк (`saveCascades`, `internal/store/cascade.go`): по
   таблице `cascadeKinds` строки целиком копируются во временные таблицы
   соединения писателя (`CREATE TEMP TABLE ... AS SELECT *`), плюс identity
   удаляемых ролей (`component_id`, `name_norm`);
3. `DeleteSourceFiles`, проход 1 (`insert`), сброс буферов;
4. возврат каскадных строк (`restoreCascades`), затем возврат указателей;
5. проход 2 и производные факты, как раньше.

Что возвращается и при каком условии:

| Таблица | Снимается | Возвращается, если |
|---|---|---|
| `role_right` | права удаляемых ролей из НЕудаляемых файлов | роль с той же identity снова есть; `role_id` переводится на её новый id, `object_id` сохраняется, если объект есть |
| `object_data_edge` | рёбра, у которых конец в удаляемом объекте и ни одной зависимости от удаляемых файлов | оба конца снова есть (id объекта прежний, это id `node`) |
| `object_data_edge_dep` | зависимости снятых рёбер | ребро вернулось |
| `object_badge` | бейджи удаляемых объектов | объект снова есть |

Id строк возвращаются прежними. Занять их некому: удалила их эта же
транзакция, а проход 1 в эти таблицы не пишет (права публикуются проходом 2,
рёбра и бейджи после него). Возврат идёт до прохода 2, поэтому пересчёт
бейджей (`publishCodeObjectEdges`: `carryStaleBadges`, `DeleteObjectBadges` по
scope) видит то же состояние, что и без удаления, и работает по прежним
правилам. Каскадные строки возвращаются раньше указателей: возврат указателя
ищет строку по прежнему id.

Для `role.object_id`: `EnsureRole` больше не стирает заполненный объект пустым
(`COALESCE(excluded.object_id, role.object_id)`). Публикация `Rights.xml`
объекта роли не знает, и теперь обе сборки дают указатель на объект роли.

Почему это корректно. Строка файла вне переопубликования этой транзакцией не
пересчитывается; её прежнее состояние и есть правильное, пока владелец под той
же identity существует: права адресуют роль по имени, рёбра и бейджи адресуют
объект по `node`. Владелец не вернулся (удалён, переименован, сменил вид):
строка не возвращается, как её не дала бы и чистая пересборка (ссылка права на
роль по имени пропала, у ребра нет конца).

Полнота закреплена тестом `TestCascadeKindsCoverCrossFileCascades`: из схемы
выводится множество таблиц, строки которых удаление `source_file` сносит
(прямо или каскадом), и каждый столбец с `ON DELETE CASCADE` на такую таблицу
обязан быть либо в `cascadeKinds`, либо в `sameFileCascades` (дочерняя строка
всегда того же файла, что и владелец, и уходит законно: параметры и запросы
символа, ссылки и их производные, члены объекта). Поведение закреплено
сценариями «правка XML роли», «правка XML регистра», «правка XML документа» и
расширенным «все указатели» построчного теста; мутация «строки не
возвращаются» красит сценарии роли и регистра.

## Отвергнутые варианты

**Upsert строки-владельца по identity вместо DELETE+INSERT.** Для
`metadata_object` это тот же вариант, что отвергнут в ADR-037: смена
контракта публикации раздела 15 (факты файла сносятся каскадом
`DELETE source_file`), сверка всех столбцов и дочерних строк
(`metadata_member`, формы). Для `role` дешевле (одна таблица, есть
`ON CONFLICT`), но строка роли уходит каскадом от `source_file` раньше, чем
публикация до неё доберётся; сохранить её значит отвязать `role.file_id` от
каскада, то есть менять схему ради одной таблицы, а рёбрам и бейджам это не
поможет.

**Добавлять в дельту файлы-источники зависимых фактов.** Для роли это один
`Rights.xml`, но его надо перечитать с диска (гидратированная запись фактов
не несёт), а для регистра это модули и XML всех документов, пишущих в него:
на `ut_demo` десятки и сотни файлов на популярный регистр, то есть цена растёт
с популярностью объекта, а не с правкой. Бейджу файл не приписан вовсе.
Отвергнут по тем же причинам, что вариант §18.4 в ADR-037.

**Сменить `ON DELETE CASCADE` на `SET NULL` или `RESTRICT`.** У `role_right`
и рёбер графа столбец обязателен (`NOT NULL`), ослабить его значит пустить
в таблицы права без роли и рёбра без конца; `RESTRICT` заблокировал бы
удаление файла. Миграция с пересозданием таблиц.

## Последствия

**Индексы, собранные до решения, надо пересобрать.** Любой инкремент,
задевший XML роли, регистра или документа, мог молча потерять права и рёбра,
а по базе потерянную строку не увидеть. Кроме того, чистая пересборка теперь
заполняет `role.object_id`. Поэтому `SchemaVersion` поднят до 4 шагом
миграции без DDL с `needsFullRebuild`, как в ADR-037: индекс версии 2 или 3 при
первом открытии получает `needs_full_rebuild`, `EnsureFresh` планирует фоновую
полную пересборку, ответы до неё идут со `stale`. `ParserVersion` не менялся.
Переключение бинарников разных версий схемы на одном `--projects-root` каждый
раз стоит полной индексации (версия из будущего заводит новую пустую эпоху).

Стоимость (`docs/benchmarks.md`, раздел issue #11): число переопубликованных
файлов не меняется (1 на правку), снимок живёт в памяти SQLite. Его размер
равен числу строк, которые держатся за владельцев переопубликуемых файлов:
права ролей, рёбра и бейджи объектов. Худший случай, все XML объектов в одном
инкременте, уходит в фоновую полную пересборку (§18.5), где снимать нечего;
`// упрощение:` у `saveCascades` называет потолок.

**Граница: `role.file_id` после инкремента только по `Rights.xml`.** Если
в транзакции переопубликован `Rights.xml`, а XML роли нет, `publishRoleRights`
по-прежнему пишет в `role.file_id` id `Rights.xml` (упрощение, описанное у
функции). Чистая пересборка дала бы XML роли. Строки прав при этом верные,
расходится только владелец строки `role`; решению это не мешает (роль с
таким `file_id` уходит вместе с `Rights.xml` и воссоздаётся его же
публикацией), но построчное равенство в этом сценарии не выполняется.

**Граница ADR-037 про каскады закрыта.** Остаток признака
`attribution-stale` (ADR-026) прежний: он горит там, где связь честно убрана
у владельца, чей модуль не переопубликован.

## Статус

ACCEPTED.

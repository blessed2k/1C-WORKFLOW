# ADR-20. Tunables регистрируются в `parseFlags`; обход через `init()` закрыт

## Контекст

Все tunables должны жить в одном месте, по существующему паттерну настроек
проекта. Одновременно жизненный цикл процесса не меняется: никакого
spawn-per-call, выхода по таймеру и фоновых демонов. Вопрос: можно ли добавить
новые настройки, не трогая `main.go` и файл настроек `cmd/mcp1c`.

## Решение

Два новых tunable (`MCP_1C_CACHE_TTL`, `MCP_1C_CACHE_LIMIT`) регистрируются в
`parseFlags` (`cmd/mcp1c/options.go`) рядом с пятью существующими настройками, а
`newServer` передаёт их в `internal/source` одним экспортированным вызовом.
Ограничение формулируется как «жизненный цикл процесса не меняется», а не как
запрет на строку в файле настроек.

## Почему

Обход через `init()` на `flag.CommandLine` был опробован и отвергнут по
результату: он даёт два экземпляра `options`, и поля в том экземпляре, который
получает `newServer`, оказываются мертвы, потому что флаг разбирается в чужой.
Это ровно расщепление настроек на два дома, которого правило «одно место» не
допускает. Отдельный второй механизм (свой разбор окружения внутри
`internal/source`) отвергнут по той же причине: он тоже даёт два места вместо
одного, только явно.

## Последствия

Буквальное «`main.go` не трогать» ограничением не является: ограничение
касается жизненного цикла процесса. Любой следующий tunable идёт тем же путём:
`options` + флаг + `envOr("MCP_1C_*")`. Дорога через `init()` упирается в
мёртвые поля, повторно её проверять не нужно.

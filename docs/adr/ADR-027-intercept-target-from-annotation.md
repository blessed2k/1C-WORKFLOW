# ADR-27. Цель перехватчика — из аргумента аннотации; отказ вместо догадки

## Контекст

`resolve.DeriveIntercepts` строит факт перехвата метода расширением
(`&Перед`/`&После`/`&Вместо`/`&ИзменениеИКонтроль`). До этого решения парсер
BSL не сохранял строковый аргумент аннотации, и цель перехвата выводилась из
имени самого метода расширения: `TargetNameNorm = m.NameNorm`. Правило
опиралось на соглашение «перехватчик называется так же, как перехватываемый
метод».

В реальном коде соглашение не соблюдается: расширение префиксует свои методы
(`РасшБ_ОбработкаПроведения`, `РасшА_ОбработкаПроведения`), а имя цели живёт
только в аргументе — `&Вместо("ОбработкаПроведения")`. Потребители
(`app/effective.go`, `retrieve/effective.go`) фильтруют перехватчики как
`ic.TargetNameNorm == row.NameNorm`, поэтому совпадения не наступало никогда:
`get_symbol view=effective`, `get_module_structure view=effective` и
effective-aware интенты `get_context_for_task` отдавали пустой список
перехватчиков — и молча.

Цена этой немоты: `&Вместо` означает, что
базовый метод не исполняется вовсе, а инструмент показывал тело базового
`ОбработкаПроведения` как единственную правду.

Причину сняла доработка парсера (ADR-031): `bsl.Annotation{Name, Arg, HasArg}` несёт аргумент, а
неразобранный аргумент отмечается диагностикой `bsl_bad_annotation_argument`.

## Решение

**1. Цель — из аргумента, перехватчик — из имени метода.**
`TargetNameNorm = domain.NormalizeName(a.Arg)`, `InterceptorNameNorm = m.NameNorm`.
На реальном коде это разные имена, и тесты фиксируют именно это (фикстура с
`РасшБ_ОбработкаПроведения` на цель `ОбработкаПроведения`, а не с совпадающими
именами).

**2. Отказ вместо догадки.** Аннотация, из которой имя цели не выводится —
аргумента нет (`&Вместо`), скобки пусты (`&Вместо()`), аргумент не разобрался
(`&Вместо(123)`, незакрытая скобка), — факта перехвата НЕ порождает. Вместо
факта кладётся диагностика `intercept_target_unknown` (severity `warning`, с
путём модуля, именем метода и подсказкой, как поправить аннотацию).

**Почему не «пониженный confidence».** Понижать нечему. `Intercept` — точный
факт из парсера: вид перехвата, имя цели и имя перехватчика читаются
буквально. Confidence здесь относится к тому, ЧТО прочитано, а не к
вероятности того, что прочитано верно; `Provenance.Validate` запрещает
эвристику с `Confidence = 1.0` именно для того, чтобы догадка не выдавалась за
факт. «Перехват самого себя» — не менее уверенный факт, а другой и заведомо
неверный: он не «менее вероятная цель», он не цель вообще. Тихо построенный,
он и создал сегодняшнюю немоту.

**3. Диагностики отдаёт сам `DeriveIntercepts`.** Подпись стала
`DeriveIntercepts(modulePath string, mod *bsl.Module, layer domain.Layer)
([]Intercept, []domain.Diagnostic)`. Отдельный «валидатор аннотаций» рядом
разбирал бы модуль во второй раз и разошёлся бы с деривацией при первой же
правке.

**4. Кто их показывает.** `internal/app/effective.go` превращает каждую
диагностику в `Warning` ответа инструмента: без этого «перехватчиков нет» и
«цель перехватчика не разобрана» выглядят для агента одинаково — ровно та
немота, против которой всё решение. `internal/retrieve` делает то же самое
(`effectiveIntercepts` в `internal/retrieve/effective.go`, ADR-29); раньше он
диагностики отбрасывал.

**5. Конфликт `&Вместо` считается по цели.** `DetectInsteadConflicts`
группирует по `(ModulePath, TargetNameNorm)`; после смены смысла поля это
означает «по перехватываемому методу». Два расширения с `&Вместо` на один
метод несут разные имена перехватчиков, и по старому полю конфликт не
обнаруживался бы вовсе.

## Последствия

- Публичная подпись `DeriveIntercepts` изменена; вызывающие
  (`internal/app/effective.go`, `internal/retrieve/effective.go`) приведены к ней.
- `resolve.DiagInterceptTargetUnknown = "intercept_target_unknown"` — новый код
  диагностики пакета.
- Модуль расширения с битой аннотацией больше не порождает «перехват самого
  себя»: перехватчиков у такого метода в выдаче нет, но есть предупреждение.
  Раньше выдача была непустой и неверной.
- `TestDeriveInterceptsAllFourKinds` переписан под новый контракт — это смена
  контракта, а не подгонка теста под код: старая версия фиксировала
  ограничение, которого больше нет.
- Регрессия на реальной выгрузке с расширениями (`ONEC_DUMP`) проверяет сверочные пары
  через шов `internal/app`. Пара `Documents/ВходящиеПлатежи` не проверяется: в
  базовом слое у этого документа модуля объекта нет вовсе, привязывать
  перехватчик не к чему — свойство данных, не кода. Пропуск разрешён только
  этой паре и только по проверенному в индексе предусловию «в базовом слое нет
  модуля по этому пути»; отсутствие базового модуля у любой другой пары и
  любая ошибка инструмента — красные, иначе регрессия «символ перестал
  находиться» осталась бы зелёной.

## Статус

ACCEPTED.

# ADR-15. Словарь покрытия `get_context_for_task`: четыре статуса и `sufficiencyStatus`

## Контекст

`get_context_for_task` должен честно сообщать агенту, насколько подобранный
контекст покрывает обязательные для конкретного intent категории
(definition, references, callers и т.д.), не выдавая частичный результат за
полный и не молча обрезая бюджет символов.

## Решение

Спецификация вводит собственный словарь из четырёх статусов покрытия
категории: `complete_inline` (влезло целиком в ответ), `complete_via_resource`
(отдано ссылкой на ресурс плюс `suggestedNextAction`), `partial` (часть
категории отдана, `returnedCount` < `totalCount`), `missing` (не отдано
ничего). Поверх них — производный агрегат `sufficiencyStatus` с тремя
значениями, выводимый из `requiredCoverage` фиксированным правилом: все
`complete_inline` → `sufficient_inline`; нет `partial`/`missing` и есть хотя
бы один `complete_via_resource` → `requires_resource_fetch`; иначе
`insufficient`.

## Почему

Булев «хватило/не хватило контекста» отвергнут: он не различает «отдано
ссылкой, агент может дотянуть сам» (`complete_via_resource`) от «не влезло
вообще» (`missing`), а без этого различия агент не может выбрать следующий
шаг автоматически, а это прямое требование спецификации (`suggestedNextAction`).
Процент покрытия одним числом тоже отвергнут: он не показывает, какая
именно обязательная категория провисла, а карта обязательных категорий по
intent (`signature-change`, `form`, `register`, `query`, `posting`,
`rights`, `add-attribute`, `bugfix`/`unknown`) требует ответа на уровне
каждой категории отдельно, а не общего агрегата.

## Последствия

Любой новый intent, добавленный в будущем, обязан завести свою строку в
карте обязательных категорий и пройти через тот же четырёхстатусный
словарь — нельзя тихо вернуть контекст без `requiredCoverage`. Правило
вывода `sufficiencyStatus` живёт в одном месте кода и закреплено таблицей
тестов. ADR-10 показал важную оговорку: даже когда пять эталонных
сценариев §25 формально проходят, логика, питающая этот словарь
(`classifyIntent`, `expandBugfix`, `findAnchors`), может давать неверные, но
формально валидные по словарю значения. Сам словарь не гарантирует, что
подставляемые в него данные корректны: это отдельная забота.

# ADR-13. Content-addressed blob и фиксированные координаты span

## Контекст

Агенту нужны точные, устойчивые координаты фрагментов кода (span), которые
переживают инкрементальную переиндексацию и не требуют повторного чтения
живого файла с диска на каждый запрос — а живой файл может измениться между
построением индекса и обращением агента.

## Решение

Индекс хранит файл как content-addressed blob (`compress/flate`,
дедупликация по хэшу содержимого, `unreferenced_since` + TTL 30 минут для
GC); все spans считаются относительно blob, живой файл для тел символов не
читается никогда. Координаты span зафиксированы: байтовые смещения 0-based
полуинтервалом по сырым байтам (включая BOM и CRLF), строки 1-based,
колонки 1-based в Unicode code points. Инвариант, проверяемый golden-тестами:
`blob[start:end]` == исходный фрагмент.

## Почему

Хранить только путь к файлу и смещение, читая тело символа с диска по
запросу, отвергнуто: живой файл может измениться (редактирование, `git
checkout`) между построением индекса и обращением агента, и span «поплывёт»
без предупреждения — тихое искажение текста хуже явной ошибки.
Content-addressed blob фиксирует ровно те байты, на которых span был
посчитан; протухание становится явной ошибкой (`resource_expired`), а не
молчаливым расхождением. Байтовые, а не рунные, смещения выбраны, чтобы
избежать двойного пересчёта позиций между UTF-8-хранением и любым
представлением на стороне клиента. Включение BOM/CRLF в смещения (вместо их
нормализации перед подсчётом) выбрано, чтобы spans совпадали 1:1 с байтами
реального файла на диске, а не с нормализованной копией, которую пришлось
бы держать и поддерживать отдельно.

## Последствия

Размер индекса растёт на объём сжатых blob-ов (бюджет — не более 2× объёма
исходников). GC неиспользуемых blob-ов — отдельный фоновый механизм с TTL,
корректность которого нужно поддерживать при каждом инкременте, а не
проверять состояние «живо/мертво» вручную на каждый запрос. Любой
потребитель span обязан адресоваться через blob, а не напрямую через
файловую систему — это исключает случайное чтение «текущего» файла в обход
индекса, но требует, чтобы каждый будущий путь работы со spans (например,
diff-инструмент) сознательно проходил через тот же blob-слой.

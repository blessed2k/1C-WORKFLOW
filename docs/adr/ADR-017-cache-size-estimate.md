# ADR-17. Размер записи оценивается один раз при вставке, наружу уходят числа, а не значения

## Контекст

Сравнение с потолком требует размера записи кэша, но точного размера у значения
типа `any` в Go нет. Одновременно `server_info` должен показывать состав кэша
выгрузки: проект, коллекции, размер, возраст обращения.

## Решение

Размер значения оценивается обходом по `reflect` с ограничением глубины ровно
один раз, сразу после `build()`, и записывается в `cacheEntry`; суммарная оценка
поддерживается инкрементально при вставке, сбросе и вытеснении. Наружу кэш отдаёт
единственный новый контракт — неизменяемую сводку `CacheSnapshot() CacheStats`
(TTL, потолок, суммарная оценка, срез записей: проект, вид коллекции, оценка,
возраст последнего обращения). Число называется оценкой и в API, и в ответе
инструмента.

## Почему

Точный размер отвергнут: для `any` его нет без ручного учёта в каждом виде
коллекции, а такой учёт пришлось бы поддерживать при каждом изменении структур
выгрузки. Пересчёт размеров на каждом тике отвергнут: он превратил бы «сдувание
в простое» в постоянную работу, а на пустом кэше работы быть не должно. Отдача самих
значений кэша (или их дампа) в `server_info` отвергнута: MCP-ответ читает модель
с конечным контекстом, дозировка — существующее правило проекта (`filterTree`,
`dosage_test.go`), и дамп коллекций сделал бы `server_info` самым тяжёлым ответом
сервера.

## Последствия

Числа в `server_info` и в замерах сравнимы между собой, но не сходятся с RSS и не
должны: это оценка структуры, а не занятая куча. Потолок по умолчанию осмыслен
только в этой же шкале — изменение алгоритма оценки молча меняет смысл потолка и
всех уже записанных замеров, поэтому менять его надо вместе с числами в
`docs/benchmarks.md`. Глубина обхода ограничена, значит глубоко вложенная
структура систематически недооценивается — новый вид коллекции получает оценку
автоматически, но не обязательно честную.

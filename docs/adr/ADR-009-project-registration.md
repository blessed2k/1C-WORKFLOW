# ADR-9. Регистрация проекта повешена на `reindex`, а не на новый инструмент (D06)

## Контекст

Нарезка тасков 11–15 предполагала, что регистрация проекта в
`workspace.Registry` (какой проект активен, где лежит его манифест) уже
решена более ранними тасками, и не проверяла эту зависимость отдельно.

## Решение

При написании `docs/install.md` (таск 16) обнаружено, что ни один
MCP-инструмент не вызывал `Registry.Upsert`/`SetActiveProject` — только
тестовые хелперы. Без этого ни один из 11 обязательных инструментов не
работал у реального пользователя, только через ручную правку
`.mcp1c/registry.json`. Уже существующий инструмент `reindex` (с таска 10,
не отдельный 12-й инструмент) получил опциональное поле `projectRoot`:
`Projects.EnsureProjectActive` регистрирует проект и делает его активным
при первом вызове.

## Почему

Заводить отдельный явный `register_project`-инструмент не рассматривалось —
это двенадцатый инструмент сверх одиннадцати, заявленных брифом.
Регистрация повешена на уже существующий `reindex` тем же приёмом
валидации пути, что уже использует `RegisterTemporary`
(`filepath.Abs`+`EvalSymlinks`); `SafeJoin` здесь не подошёл по смыслу,
потому что `projectRoot` типично лежит вне `workspaceRoot`, а не внутри
него.

## Последствия

Продукт стал end-to-end рабочим без нового инструмента в контракте, но само
обнаружение настолько позднее — таск 16 из 16, при написании документации
установки — обнажает критический пробел в собственной нарезке тасков 11–15:
они предполагали эту зависимость уже решённой и не проверяли её отдельно.
Подтверждено обеими осями ревью.

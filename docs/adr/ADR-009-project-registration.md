# ADR-9. Регистрация проекта повешена на `reindex`, а не на новый инструмент

## Контекст

Индексные инструменты предполагали, что регистрация проекта в
`workspace.Registry` (какой проект активен, где лежит его манифест) уже
где-то решена, и эту зависимость отдельно никто не проверял.

## Решение

При написании `docs/install.md` обнаружено, что ни один MCP-инструмент не
вызывал `Registry.Upsert`/`SetActiveProject`, только тестовые хелперы. Без
этого ни один из 11 индексных инструментов не работал у реального
пользователя, только через ручную правку `.mcp1c/registry.json`. Уже
существующий инструмент `reindex` получил опциональное поле `projectRoot`:
`Projects.EnsureProjectActive` регистрирует проект и делает его активным при
первом вызове.

## Почему

Отдельный явный инструмент `register_project` отвергнут: это двенадцатый
инструмент сверх заявленных одиннадцати. Регистрация повешена на уже
существующий `reindex` тем же приёмом валидации пути, что использует
`RegisterTemporary` (`filepath.Abs`+`EvalSymlinks`). `SafeJoin` здесь не
подходит по смыслу: `projectRoot` типично лежит вне `workspaceRoot`, а не
внутри него.

## Последствия

Продукт стал рабочим end-to-end без нового инструмента в контракте. Пробел
нашёлся только при написании документации установки: зависимость, которую
все считали решённой, нужно проверять сквозным сценарием с реальной
регистрацией проекта, а не тестовыми хелперами.

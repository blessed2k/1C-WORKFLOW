# ADR-10. Три точечных фикса `get_context_for_task` поверх принятого таска (D07)

## Контекст

Таск 15 сдал `get_context_for_task` принятым — пять эталонных сценариев §25
проходили. Предполагалось, что это доказывает корректность классификации
intent, глубины `callers` для `bugfix` и порядка поиска anchors.

## Решение

Собственный eval-прогон таска 16 (`evals/runner`, 12 реалистичных задач
против `ut_demo`, R76) нашёл три логических дефекта: (1) `classifyIntent`
матчил лексикон подстрокой без границы слова — «прав» ложно голосовал из
середины «поправь»/«справочник»; (2) `expandBugfix` гонял `callers` на
`bctx.maxDepth` вместо `1` (17 вместо 7 на реальном символе), тогда как
`expandSignatureChange` уже использовал `1` для той же категории — контракт
между двумя builder'ами был рассогласован; (3) `findAnchors` шёл одним
интерливным проходом, и одноимённый обработчик формы съедал весь
`maxAnchors=6` до того, как объект-владелец формы попадал в список — все 4
обязательные категории `intent=form` честно, но неверно уходили в `missing`.
Исправления точечные: `containsAtWordBoundary` (только левая граница —
стемы лексикона намеренно без окончаний), `callers` глубины `1` литералом,
`findAnchors` в три раздельных прохода по убыванию специфичности
(структурные → объекты метаданных → голые символы).

## Почему

Оставить как есть, раз пять эталонных сценариев §25 формально проходят, не
рассматривалось: сценарии не покрывали эти три конкретных кейса
(лексикон-подстрока, глубина `callers`, порядок `anchors`), а eval-корпус
из 12 задач их вскрыл. Переписать scoring-модель целиком вместо точечных
фиксов не рассматривалось — три причины расходятся по коду (классификатор,
expansion, anchor-поиск), и локализованное исправление каждой дешевле и
безопаснее регрессии, чем общий рефакторинг.

## Последствия

Три регрессионных теста (fixture + realdump) закрывают найденные кейсы;
числа до/после подтверждены живым JSON-RPC на `ut_demo`. Сознательно НЕ
тронуты смежные находки того же eval-прогона: §4.2 (регистр определяется
данными в generic-механизме проведения УТ — архитектурный слепой угол
статического анализа, не баг), §4.4 (anchor на реквизите без префикса
типа), §4.5 (лимит `profiles` — задокументированное ограничение v1).
`get_context_for_task` принят с известными смежными ограничениями, а не с
исчерпывающим покрытием — граница между «исправлено» и «документированный
долг» проведена явно в отчёте, а не скрыта.

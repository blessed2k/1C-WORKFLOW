# ADR-3. Стратегия разбора BSL

- **Статус:** PROPOSED (DoD фазы 0B по разделу 34 архитектуры: ADR утверждается
  отдельно). Решение (d) реализовано в `internal/parse/bsl`.
- **Дата проекта:** 17.08.2026
- **Фаза:** 0B (`docs/architecture-index.md`, разделы 12, 18.3, 34)
- **Решает:** чем индексный MCP разбирает BSL — чужой грамматикой, чужим
  анализатором или собственным парсером, и что из этого выдерживает
  `CGO_ENABLED=0` на macOS и Windows.
- **Не решает:** разбор XML метаданных (`internal/parse/meta`) и языка запросов
  (`internal/parse/query`); модель расширений (ADR-4); production-схему фактов
  (фаза 3).

> Спайк и его машинные результаты удалены из публичного дерева после принятия решения;
> пути `spikes/...` ниже сохранены как история. Фикстуры оракула парсера живут в
> `internal/parse/bsl/testdata/oracle`.

Заполнен по результатам spike в `spikes/parser/`. Машинные результаты — каталог
`spikes/parser/results/`: `parser-c.json` (скорость и факты), `parser-c-stream.json`
(память), `fuzz-60s.txt` (устойчивость), `oracle/*.json` и `oracle-compare.json`
(независимая сверка). Все числа ниже получены на одной машине
за один день; ограничения замера — раздел 6.

---

## 1. Контекст

Раздел 12 архитектуры оставил стратегию парсера открытой и назвал четыре
кандидата и обязательный чеклист. Регулярки текущего кода отвергнуты заранее:
в репозитории уже два разных парсера экспортных методов, и они расходятся на
многострочных сигнатурах.

Жёсткие рамки, внутри которых вообще есть выбор:

- **D1** (журнал решений, приложение A `docs/architecture-index.md`):
  production-сборка строго `CGO_ENABLED=0` на macOS и Windows, без
  GCC/MinGW/DLL. Всё, что не собирается в этом режиме, отсеивается до разговора
  о качестве.
- **§18.3**: координаты span зафиксированы ДО spike и обязательны к соблюдению:
  байтовые смещения 0-based по сырым байтам (включая BOM и CRLF), строки 1-based,
  колонки 1-based в Unicode code points, `blob[start:end]` == исходный фрагмент.
- **§34**: spike живёт отдельным вложенным модулем и не импортируется production-кодом.

## 2. Что и как проверялось

Корпус — весь BSL реальной выгрузки (демо-база УТ 11.5): **12 434 файла,
516 097 644 байта**. Путь передан через `ONEC_DUMP`, в репозиторий не попадает.
Плюс золотой набор из шести фикстур под чеклист §12 и дефектные входы.

| Замер | Как получен |
|---|---|
| precision/recall | золотой набор `spikes/parser/testdata/golden`, разметка `expected.json` написана руками по тексту фикстур; счётчики — `EvaluateGolden` |
| независимая сверка | `bsl-language-server` 1.0.3 (`document_symbols`) на трёх реальных модулях; сырые ответы сохранены, сравнение машинное — `go run ./cmd/oraclecmp` |
| инвариант span | прогон по всем 12 434 файлам: `src[start:end]` сверяется с именем символа и ссылки |
| скорость cold | `go run ./cmd/spikerun`, один поток, корпус в памяти |
| скорость инкремента | повторный разбор одного модуля, 300 файлов, медиана и p95 |
| память | `go run ./cmd/spikerun -stream`: файл читается, разбирается и выбрасывается |
| устойчивость | `go test -fuzz`, 60 с |
| deployment | реальные команды сборки, раздел 4.4 |

Машина: macOS 25.5.0 (darwin/arm64), Apple M5, 10 ядер, Go 1.26.5, APFS.

**Не проверено, с причиной:**

- precision/recall кандидатов (a) и (b) — не измерялись: оба отсеяны по deployment
  до замера качества (4.4). Это результат по критерию deployment, а не пропуск проверки.
- полный прогон оракула по всем 12 434 файлам — не делался: сверены три модуля (4.3).
  Сама сверка машинная и воспроизводимая, ограничен именно охват.
- поведение на Windows — не проверялось: Windows-машины нет (то же ограничение, что у ADR-2).
- многопоточный разбор — не мерился: все цифры однопоточные.
- `#Вставка` / `#Удаление` расширений и `ИзменениеИКонтроль` — распознаются как
  препроцессор и аннотации, но отдельной семантики в spike нет: это зона ADR-4.

### 4.3 Независимая сверка с оракулом

`bsl-language-server` 1.0.3, `document_symbols`, три реальных модуля разной природы.
Сравнивались множество имён методов и число параметров каждого.

**Артефакты, чтобы сверку можно было перепроверить, а не поверить на слово:**

- сырые ответы оракула — `spikes/parser/results/oracle/*.json` (путь к выгрузке
  в них заменён на `${ONEC_DUMP}`: пути к выгрузкам в репозиторий не коммитятся);
- машинное сравнение — `spikes/parser/results/oracle-compare.json`, получено
  `ONEC_DUMP=… go run ./cmd/oraclecmp` из `spikes/parser`. Команда сама читает
  ответы оракула, разбирает те же файлы парсером и завершается с кодом 1 при
  любом расхождении. Последний прогон: код 0, расхождений 0.

| Модуль | Методов у оракула | Методов у (c) | Только у оракула | Только у (c) | Расхождений по числу параметров |
|---|---|---|---|---|---|
| `CommonModules/ОбменДаннымиСервер/Ext/Module.bsl` | 415 | 415 | 0 | 0 | 0 |
| `Documents/РеализацияТоваровУслуг/Forms/ФормаДокумента/Ext/Form/Module.bsl` | 429 | 429 | 0 | 0 | 0 |
| `AccumulationRegisters/ДвиженияПоПрочимАктивамПассивам/Ext/ManagerModule.bsl` | 9 | 9 | 0 | 0 | 0 |
| **итого** | **853** | **853** | **0** | **0** | **0** |

Две реальные ошибки парсера нашлись именно на корпусе, а не на своих фикстурах,
и обе теперь закрыты тестами:

1. `Обработчик.Процедура = "…"` — поле объекта с именем ключевого слова
   разбиралось как начало объявления. Давало 1 062 «незакрытых» метода.
2. Многострочный литерал обрывался на пустой строке и на строке-комментарии `//`

После исправлений на всём корпусе: **0 файлов с диагностиками, 0 незакрытых методов,
0 нарушений span**.

### 4.4 Deployment: что именно не собралось

Кандидат (a), нативные биндинги. Команды и вывод дословно:

```
go get github.com/tree-sitter/go-tree-sitter        # v0.25.0, ок
CGO_ENABLED=0 go build ./...                        # ./main.go:9:30: undefined: ts.NewParser
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./...  # ./main.go:9:30: undefined: ts.NewParser
CGO_ENABLED=1 go build ./...                        # ок, код возврата 0
CGO_ENABLED=0 go list -f '{{.GoFiles}}' github.com/tree-sitter/go-tree-sitter
  # [logger.go] — весь остальной пакет (parser.go, node.go, tree.go, query.go, …) игнорируется
```

То есть при `CGO_ENABLED=0` пакет отдаёт единственный файл и ни одной функции
API. Отказ ровно по D1, не по качеству грамматики.

Кандидат (a), маршрут через WASM. Грамматика `tree-sitter-bsl@0.1.7` (MIT,
alkoleft) в npm-пакете содержит `grammars/bsl/src/parser.c`, `grammar.json` и
нативные `prebuilds/*.node` для шести платформ, **готового `.wasm` в пакете нет**
(проверено `npm pack` + `tar tzf`). Собрать `.wasm` на этой машине нечем:

```
command -v emcc          -> НЕТ
command -v tree-sitter   -> НЕТ
command -v cargo         -> НЕТ
clang -print-targets | grep -i wasm  -> пусто (Apple clang без wasm-таргета)
docker info              -> failed to connect ... daemon is not running
```

Сверх этого: даже собранный грамматический `.wasm` штатно исполняется через
`web-tree-sitter`, который грузит грамматику как emscripten side module
динамическим связыванием; `wazero` динамическое связывание модулей не
поддерживает, поэтому связка «grammar.wasm + wazero» требует не сборки
грамматики, а отдельного хоста под tree-sitter runtime. Это не измерение, а
известное свойство обоих инструментов, и оно записано как аргумент, а не как
цифра: на этой машине проверить его было нечем.

Кандидат (b), стоимость старта:

```
java -jar bsl-language-server-1.0.3-exec.jar --analyze --srcDir ./blstiny --reporter console
  # 5.494 s wall, 20.66 s user CPU — на ОДИН файл в 18 строк
```

Как runtime-зависимость отклоняется по D1 (Java рядом с pure-Go сервером) и по
стоимости старта. Как оракул в тестах — принимается: именно он подтвердил 4.3.

Один поток, darwin/arm64, Apple M5, Go 1.26.5. Каждая строка помечена артефактом,
из которого она взята: одного файла на всю таблицу не хватает, прогонов три.

| Метрика | Значение | Артефакт |
|---|---|---|

| cold parse, только символы (`SkipReferences`) | 3.37 с | `results/parser-c.json` |

Пик RSS основного прогона (1.03 ГиБ) — это память корпуса, который он держит
целиком ради сопоставимости замеров скорости, а не память парсера. Память парсера
показывает потоковый прогон, и это отдельный запуск с отдельным артефактом.

## 5. Принятое решение

**Кандидат (d): собственный tolerant lexer/parser на Go как runtime,
`bsl-language-server` как оракул в тестах и опциональное второе мнение — не в runtime.**

Обоснование по критериям, в порядке жёсткости:

1. **Deployment.** Единственный кандидат, который собирается `CGO_ENABLED=0` на
   обеих целевых платформах: у него ноль внешних зависимостей. (a) не собирается
   вовсе (4.4), (b) тащит JVM.
2. **Контракт span.** §18.3 требует байтовых смещений по сырым байтам и колонок в
   code points. Своим парсером это выполняется по построению и проверено на всём
   корпусе; у чужой грамматики это было бы слоем конверсии поверх её собственных
   координат.
3. **Скорость.** Полный корпус за 4.4 с и инкремент за 77 мкс закрывают бюджет
   индексации с запасом; стоимость старта нулевая, что важно для процесса, который
   поднимается на каждый запуск клиента.
4. **Качество.** На 853 методах трёх реальных модулей — полное совпадение с
   независимым анализатором; на всём корпусе ноль диагностик и ноль нарушений span.

Стоимость решения признаётся честно: собственный парсер — это код, который надо
сопровождать, и его согласие с платформой держится на тестах, а не на грамматике
из экосистемы. Поэтому (b) остаётся в контуре как оракул: расхождение с ним —
дефект парсера, пока не доказано обратное.

## 6. Ограничения измерений

1. **Одна машина, одна ОС, один диск.** darwin/arm64, APFS. Windows-цифр нет —
   то же ограничение, что у ADR-2.
2. **Одна выгрузка** — демо-база УТ 11.5. Другие конфигурации и рукописный код
   заказчиков могут содержать идиомы, которых здесь нет; две уже найденные ошибки
   (4.3) — прямое доказательство, что корпус решает.
3. **Золотой набор написан автором парсера.** Его 1.0 означает согласие с
   разметкой, а не с платформой. Вес несёт сверка 4.3, а не таблица 4.1.
4. **Оракул проверен на трёх модулях, не на корпусе.** Полный прогон
   `bsl-language-server` по 12 434 файлам не делался: при 5.5 с старта на файл это
   отдельная работа. Сравнение трёх модулей воспроизводится командой из 4.3.
5. **Сверялись имена методов и число параметров**, не типы, не тела, не
   области видимости переменных. Совпадение 853/853 — это совпадение по символам.
6. **Файловый кеш ОС не контролировался**, поэтому «холодный» относится к
   состоянию парсера, а не диска.
7. **Все замеры однопоточные.** Параллельный разбор пайплайна индексации не мерился.
8. **Кандидаты (a) и (b) не сравнивались по качеству** — см. 4.2.

## 7. Последствия для реализации

- `internal/parse/bsl` реализуется по решению (d). Публичная форма
  `Parse(src []byte, opts Options) (*Module, []domain.Diagnostic)` в spike уже
  соблюдена, перенос идёт без смены сигнатуры.
- Инварианты, которые обязаны переехать вместе с кодом и остаться в тестах:
  контракт §18.3 на всём корпусе; ноль ложных вызовов в строках и комментариях;
  error recovery без потери методов; fuzz без паник.
- Обе ошибки из 4.3 закреплены тестами (`realworld_test.go`) — они переезжают
  в production-набор, иначе будут найдены заново.
- `bsl-language-server` остаётся в контуре тестов как оракул. В runtime он не
  подключается ни при каких условиях.
- Регулярочные парсеры экспортов в `internal/source` остаются как compat-слой
  существующих инструментов и новым кодом не используются.

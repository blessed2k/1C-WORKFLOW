# Подключение: подробности

Основной порядок установки и быстрый старт описаны в [README.md](../README.md). Здесь то,
что туда не поместилось: другие клиенты, запуск из исходников, манифест с расширениями, как
устроена регистрация проекта и как проверить сервер вручную.

Сервер не меняет конфиги MCP-клиентов сам: записи ниже добавляются пользователем.

## Запуск из исходников

Вместо собранного бинарника можно запускать `go run`: компиляция и старт за один шаг, дольше
на холодную, зато не нужна пересборка после правки кода сервера.

```json
{
  "mcpServers": {
    "1c-workflow-dev": {
      "command": "go",
      "args": ["run", "./cmd/mcp1c", "--projects-root", "<каталог workspace>"],
      "cwd": "<каталог репозитория>"
    }
  }
}
```

Рабочим каталогом процесса должен быть корень репозитория (поле `cwd`, если клиент его
поддерживает).

## Claude Code

Команда из README пишет запись в конфиг Claude Code. Переменные окружения задаются ключом
`-e`:

```sh
claude mcp add 1c-workflow \
  -e MCP_1C_PROJECTS_ROOT=<каталог workspace> \
  -e MCP_1C_DUMP=<каталог выгрузки> \
  -- mcp1c
```

Тот же сервер можно завести второй записью для живой базы (`1c-workflow-live` с
`MCP_1C_BASE_URL`, `MCP_1C_USER`, `MCP_1C_PASSWORD`): бинарник один, различаются только
параметры запуска.

## Codex CLI

`~/.codex/config.toml`, секция `[mcp_servers.<имя>]`:

```toml
[mcp_servers."1c-workflow"]
command = "mcp1c"
args = ["--dump", "<каталог выгрузки>", "--projects-root", "<каталог workspace>"]

[mcp_servers."1c-workflow".env]
MCP_1C_SYNTAX_INDEX = "<файл индекса синтаксиса>"
```

Codex CLI не задаёт рабочий каталог MCP-сервера, поэтому для него удобнее собранный
бинарник, а не `go run`.

## Несколько живых баз

Файл для `--bases` (`MCP_1C_BASES`):

```json
[
  { "name": "test", "url": "http://<хост>/<база>/hs/mcp-1c", "user": "<пользователь>", "password": "<пароль>" },
  { "name": "copy", "url": "http://<хост>/<копия>/hs/mcp-1c", "user": "<пользователь>", "password": "<пароль>" }
]
```

Записи без `name` или `url` пропускаются. При одной базе она выбирается сразу, при нескольких
сервер стартует без выбранной, и базу выбирают `set_base`. Разовый вызов к другой базе без
переключения: аргумент `base=<имя>` у live-инструментов. Пароли в файле открытым текстом:
храните его вне репозиториев с правами только для своего пользователя.

## Манифест проекта

`1c-project.json` лежит в корне проекта и описывает его компоненты. Минимальный пример есть в
README. Проект с конфигурацией и двумя расширениями, выгрузки которых лежат в разных
каталогах:

```json
{
  "version": 1,
  "project": "trade",
  "displayName": "Торговля и расширения",
  "components": [
    { "id": "cfg", "kind": "configuration", "root": "." },
    { "id": "ext-a", "kind": "extension", "root": "../../Расширения/РасширениеА",
      "appliesTo": "cfg", "applyOrder": 1 },
    { "id": "ext-b", "kind": "extension", "root": "../../Расширения/РасширениеБ",
      "appliesTo": "cfg", "applyOrder": 2 }
  ]
}
```

Правила:

- `project` и `id` компонентов: до 64 символов, строчная латиница, цифры, `-`, `_` и `.`,
  первым идёт буква или цифра.
- `root` относительный; подъём через `..` разрешён, абсолютный путь отклоняется, чтобы
  манифест читался на другой машине с другим корнем дерева.
- Корни компонентов не могут совпадать или быть вложены друг в друга.
- Файлы компонента не выходят за его корень: граница проверяется для каждого пути.
- Виды компонентов: `configuration`, `extension`, `external-data-processor`,
  `external-report`, `test-sources`, `standalone-bsl`.
- `appliesTo` и `applyOrder` у расширения задают, к какой конфигурации и в каком порядке оно
  применяется в объединённом виде (`view=effective`). Настоящий порядок применения в базе
  из выгрузки не выводится, поэтому конфликт двух `&Вместо` на одном методе отдаётся
  предупреждением, а не выбором победителя.
- Необязательные `include` и `exclude` (у проекта и у компонента) сужают набор файлов.

## Регистрация проекта и индекс

Индексные инструменты работают с проектом, записанным в реестр
`<projects-root>/.mcp1c/registry.json`. Регистрирует проект только `reindex` с `projectRoot`:

```json
{"name": "reindex", "arguments": {"projectRoot": "<каталог с 1c-project.json>"}}
```

- Первый вызов с новым каталогом регистрирует проект, делает его активным и строит полный
  индекс (если `mode` не задан).
- Повторный вызов с уже известным каталогом только активирует проект и обновляет индекс.
- Без `projectRoot` `reindex` обновляет активный проект: `mode=incremental` (по умолчанию)
  или `mode=full`; `component` сужает пересборку до одного компонента.
- `set_dump` и `--dump` активируют зарегистрированный проект, в манифесте которого эта
  выгрузка описана компонентом. Если такого нет, индексные инструменты отвечают
  `no_active_project` с подсказкой про `reindex projectRoot`.
- Без `--dump` активен проект, сохранённый в реестре, или единственный зарегистрированный.
- При вызове индексных инструментов сервер проверяет, изменились ли файлы, и дочитывает их.
  Отдельный `reindex` нужен после массовых изменений, например новой выгрузки поверх старой.
- Реестр и файлы индекса относятся к локальному состоянию, в git их не кладут.
- Индекс строится только из файлов на диске, живая база в нём не участвует.

## Проверка вручную

Сервер говорит по MCP 2025-06-18 поверх stdio: JSON-RPC, один объект на строку, первым
сообщением `initialize`. `stdout` занят протоколом, диагностика пишется в `stderr`.

```text
--> {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-06-18","capabilities":{},"clientInfo":{"name":"my-client","version":"0.1"}}}
<-- {"jsonrpc":"2.0","id":1,"result":{"capabilities":{...},"instructions":"...","protocolVersion":"2025-06-18","serverInfo":{"name":"1C-WORKFLOW","version":"0.1.0"}}}

--> {"jsonrpc":"2.0","method":"notifications/initialized"}

--> {"jsonrpc":"2.0","id":2,"method":"tools/list"}

--> {"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"index_status","arguments":{}}}
```

Что ожидать:

1. `serverInfo.name` равно `1C-WORKFLOW`.
2. `index_status` до регистрации проекта отвечает ошибкой (`isError: true`) с кодом
   `[no_active_project]` и подсказкой вызвать `reindex` с `projectRoot`. Если сервер запущен
   без `--projects-root`, индексных инструментов в `tools/list` нет вовсе.
3. `reindex` с `projectRoot` возвращает `generation`, длительность, счётчики по компонентам
   (`filesChanged`, `filesRemoved`, `symbols`) и тайминги этапов.
4. `find_symbol` с `{"name": "<имя процедуры>"}` находит процедуру из выгрузки.

Если индекс синтаксиса не собран, в `stderr` при старте будет одна строка предупреждения, на
протокол это не влияет.

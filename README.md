# 1C-WORKFLOW

[English version](README.en.md)

MCP-сервер для разработки на 1С:Предприятии (встроенный язык, метаданные, запросы). Даёт
ИИ-агенту (Claude Code, Codex и любому другому MCP-клиенту) точные ответы о конкретной
конфигурации вместо чтения тысяч XML-файлов и догадок по памяти.

Три источника данных за одним процессом `mcp1c`:

- **offline**: XML-выгрузка конфигурации (`DumpConfigToFiles`), читается по требованию;
- **индекс**: персистентный SQLite-индекс символов, ссылок, графа вызовов, метаданных,
  запросов и обращений к регистрам с инкрементальным обновлением;
- **live**: живая база через расширение-коннектор с HTTP-сервисом, строго только чтение.

Один статически собранный бинарник без cgo, транспорт stdio, протокол MCP 2025-06-18.

## Зачем

Примеры задач, на которых агент без сервера тратит много чтения и часто ошибается:

- **Поменять сигнатуру процедуры.** `find_references`, `trace_call_graph` и `find_impact`
  показывают всех вызывающих и то, что зависит от процедуры, до правки, а
  `get_context_for_task` одним вызовом собирает минимальный контекст по описанию задачи.
- **Добавить код в запись или проведение документа.** `write_path` перечисляет всё, что
  выполняется при записи (модуль объекта, подписки, движения, регистрация в обменах),
  `get_movements review=true` разбирает код проведения.
- **Написать запрос и не ошибиться в полях.** `get_query_schema` отдаёт точные имена полей и
  параметры виртуальных таблиц, `query_advisor` проверяет готовый текст на анти-паттерны и
  неиндексированные отборы, в live `execute_query` выполняет SELECT на реальных данных.
- **Разобраться, почему пользователь не видит объект или объект не ушёл в обмен.**
  `visibility_audit`, `rights_audit`, `access_diagnose` и `exchange_audit` проходят цепочку
  подсистем, функциональных опций, ролей, профилей и планов обмена.

Сервер ничего не меняет ни в конфигурации, ни в базе: все инструменты только читают, кроме
`reindex`, который пишет собственный индекс.

## Требования

- **ОС**: Windows, macOS или Linux, amd64 или arm64.
- **Go 1.26+**: только для сборки из исходников и для `go install`.
- **XML-выгрузка конфигурации** в формате `DumpConfigToFiles` (конфигуратор или `ibcmd`), по
  желанию выгрузки расширений, внешних обработок и отчётов.
- **Установленная платформа 1С:Предприятие 8.3**: из её файлов синтакс-помощника (`.hbk`)
  один раз собирается индекс синтаксиса для `bsl_syntax` и `validate_bsl`.
- **Для live-режима**: база, в которую можно загрузить расширение, и публикация её
  HTTP-сервисов (веб-сервер или автономный сервер `ibsrv`).

## Установка

**Готовый бинарник.** Скачайте архив для своей ОС на странице
[Releases](https://github.com/blessed2k/1C-WORKFLOW/releases), распакуйте и положите `mcp1c`
(`mcp1c.exe`) и `syntaxgen` в каталог из `PATH`. Контрольные суммы лежат в `checksums.txt`.

**Через `go install`:**

```sh
go install github.com/blessed2k/1C-WORKFLOW/cmd/mcp1c@latest
go install github.com/blessed2k/1C-WORKFLOW/cmd/syntaxgen@latest
```

**Из исходников:**

```sh
git clone https://github.com/blessed2k/1C-WORKFLOW.git
cd 1C-WORKFLOW
CGO_ENABLED=0 go build -o mcp1c ./cmd/mcp1c          # Windows: -o mcp1c.exe
CGO_ENABLED=0 go build -o syntaxgen ./cmd/syntaxgen
```

Проверка: `mcp1c --version`.

## Индекс синтаксиса платформы

Справочник платформы принадлежит её правообладателю, поэтому в репозитории и в архивах
его нет: индекс собирается у вас из файлов установленной платформы.

```sh
syntaxgen <каталог платформы>/shcntx_ru.hbk \
    <каталог платформы>/shlang_ru.hbk <каталог платформы>/shquery_ru.hbk
```

Из исходников то же самое: `go run ./cmd/syntaxgen <файлы .hbk>`.

| ОС | Каталог платформы |
|---|---|
| Windows | `C:\Program Files\1cv8\<версия>\bin` |
| macOS | `/opt/1cv8/<версия>` |
| Linux | `/opt/1cv8/x86_64/<версия>` |

`shcntx_ru.hbk` обязателен (глобальный контекст и типы), `shlang_ru.hbk` добавляет операторы
языка, `shquery_ru.hbk` добавляет язык запросов. После смены версии платформы индекс стоит
пересобрать.

Файл пишется в `<каталог пользовательской конфигурации>/mcp1c/syntax-index.json.gz`, где его
по умолчанию ищет сервер: `%AppData%` на Windows, `~/Library/Application Support` на macOS,
`$XDG_CONFIG_HOME` или `~/.config` на Linux. Другой путь: `syntaxgen -out <файл>` и у сервера
`--syntax-index <файл>` (или `MCP_1C_SYNTAX_INDEX`).

Без индекса сервер работает: в stderr пишется предупреждение, `bsl_syntax` и `validate_bsl`
отвечают ошибкой с командой сборки, а индексный слой не отличает вызовы платформенных
функций от вызовов своих процедур.

## Быстрый старт в Claude Code

**1. Разложите проект.** Манифест `1c-project.json` описывает, из чего состоит проект:

```text
my-project/
  1c-project.json
  src/               <- XML-выгрузка конфигурации (Configuration.xml и каталоги объектов)
```

```json
{
  "version": 1,
  "project": "my-project",
  "displayName": "Моя конфигурация",
  "components": [
    { "id": "cfg", "kind": "configuration", "root": "src" }
  ]
}
```

Виды компонентов: `configuration`, `extension` (с `appliesTo` и `applyOrder`),
`external-data-processor`, `external-report`, `test-sources`, `standalone-bsl`. Корень
компонента задаётся относительным путём и может выходить за каталог манифеста через `..`,
абсолютные пути не принимаются. Пример с расширениями есть в [docs/install.md](docs/install.md).

**2. Подключите сервер.** `--projects-root` задаёт каталог, где сервер держит реестр проектов
и файлы индекса (`<projects-root>/.mcp1c/`); без него индексных инструментов нет.

```sh
claude mcp add 1c-workflow -- mcp1c \
  --dump /path/to/my-project/src \
  --projects-root /path/to/workspace
```

`--scope user` сделает сервер доступным во всех проектах. Каталог `.mcp1c/` не коммитьте.

**3. Постройте индекс.** Первый раз проект регистрируется вызовом `reindex` с `projectRoot`
(каталог с `1c-project.json`). Проще всего попросить агента:

```text
Вызови reindex с projectRoot=/path/to/my-project
```

Первый полный индекс крупной типовой конфигурации занимает несколько минут, небольшой
конфигурации секунды. Дальше индекс обновляется инкрементально: при вызове индексного
инструмента сервер сам дочитывает изменённые файлы. При следующих запусках с тем же `--dump`
проект активируется автоматически.

**4. Работайте.** Пример запроса:

```text
Хочу добавить в ПередЗаписью документа ЗаказКлиента проверку даты отгрузки.
Что уже выполняется при записи и где безопаснее всего вставить код?
```

Агент получает в системный контекст карту инструментов по фазам задачи (разведка, анализ
перед изменением, написание, проверка) и сам выбирает нужные: здесь это
`get_context_for_task`, `write_path` и после написания `validate_bsl`.

**5. Хук на запись BSL (по желанию).** Агент чаще пишет свою вспомогательную функцию, чем
ищет готовую. Скрипт `tools/hooks/bsl_ready_methods.py` после записи файла `.bsl` дописывает
в контекст агента имена новых процедур и просьбу прогнать код через `validate_bsl`: тот
называет возможные готовые методы (подсказка по словам, а не находка). Хук ничего не
блокирует и в сеть не ходит; в `~/.cache/mcp1c-hooks` он помнит, о каких процедурах сессии
уже напоминал. Подключается в `settings.json` Claude Code (нужен Python 3; на Windows команда
обычно `python` или `py -3`):

```json
{
  "hooks": {
    "PostToolUse": [{
      "matcher": "Write|Edit|MultiEdit",
      "hooks": [{"type": "command", "command": "python3 /path/to/1C-WORKFLOW/tools/hooks/bsl_ready_methods.py"}]
    }]
  }
}
```

### Другие MCP-клиенты

Сервер запускается как обычный stdio-процесс, поэтому подойдёт любой клиент с общим
JSON-конфигом:

```json
{
  "mcpServers": {
    "1c-workflow": {
      "command": "mcp1c",
      "args": ["--dump", "/path/to/my-project/src", "--projects-root", "/path/to/workspace"]
    }
  }
}
```

Пример для Codex CLI, запуск через `go run` и проверка вручную по JSON-RPC описаны в
[docs/install.md](docs/install.md).

## Режимы и флаги

Режим выбирается при старте: если задан `--base` или `--bases`, сервер работает с живой
базой, иначе с выгрузкой. Выгрузку можно сменить на ходу инструментом `set_dump`, базу
инструментом `set_base`. Индексный слой (`--projects-root`) работает в обоих режимах и строится
только из файлов на диске.

Каждый флаг можно задать переменной окружения, флаг сильнее. Неразбираемое значение
переменной откатывается на значение по умолчанию.

| Флаг | Переменная окружения | По умолчанию | Назначение |
|---|---|---|---|
| `--dump` | `MCP_1C_DUMP` | | каталог XML-выгрузки (offline) |
| `--projects-root` | `MCP_1C_PROJECTS_ROOT` | | каталог реестра проектов и индексов; без него индексные инструменты не регистрируются; его же сканирует `list_projects` |
| `--base` | `MCP_1C_BASE_URL` | | URL HTTP-сервиса коннектора (live) |
| `--user` | `MCP_1C_USER` | | пользователь базы (live) |
| `--password` | `MCP_1C_PASSWORD` | | пароль (live); лучше передавать переменной окружения |
| `--bases` | `MCP_1C_BASES` | | JSON-файл со списком баз для `set_base` |
| `--tools` | `MCP_1C_TOOLS` | `full` | профиль: `full` или `core` (без редко нужных инструментов, экономит контекст); неизвестное значение даёт `full` |
| `--syntax-index` | `MCP_1C_SYNTAX_INDEX` | см. выше | файл индекса синтаксиса платформы |
| `--api-cards` | `MCP_1C_API_CARDS` | `<каталог настроек>/mcp1c/api-cards` | каталог карточек задач для `find_api` (`cmd/apicards`); `none` отключает |
| `--cache-ttl` | `MCP_1C_CACHE_TTL` | `10m` | сколько простаивает разобранная коллекция выгрузки в памяти; `0` выключает истечение |
| `--cache-limit` | `MCP_1C_CACHE_LIMIT` | `536870912` | потолок памяти кэша выгрузки в байтах; `0` выключает вытеснение |
| `--graph-chain-depth` | `MCP_1C_GRAPH_CHAIN_DEPTH` | `6` | длина цепочки, после которой каждое звено снижает уверенность ребра объектного графа |
| `--graph-hub-fanin` | `MCP_1C_GRAPH_HUB_FANIN` | `50` | число вызывающих, начиная с которого процедура считается хабом |
| `--graph-depth-penalty` | `MCP_1C_GRAPH_DEPTH_PENALTY` | `0.9` | множитель уверенности за каждое лишнее звено |
| `--graph-hub-penalty` | `MCP_1C_GRAPH_HUB_PENALTY` | `0.7` | множитель уверенности для цепочки через хаб |
| `--graph-radius-nodes` | `MCP_1C_GRAPH_RADIUS_NODES` | `300` | потолок узлов в одном ответе карты графа |
| `--version` | | | напечатать версию и выйти |

Файл `--bases` содержит массив `[{"name": "...", "url": "...", "user": "...", "password": "..."}]`.
Пароли в нём хранятся открытым текстом: держите файл вне репозиториев и с правами только для
своего пользователя. Если баз несколько, сервер стартует без выбранной базы, и выбор делается
явно через `set_base`, чтобы ответ не пришёл из чужой базы.

Активный источник, проект и профиль показывает `server_info`.

### Карта объектного графа

```sh
mcp1c graph --project /path/to/workspace [--listen 127.0.0.1:0]
```

Поднимает локальную веб-страницу с картой связей объектов по уже построенному индексу
(`--project` указывает на корень workspace, где лежит `.mcp1c`, то есть на тот же каталог, что
`--projects-root`, а не на саму выгрузку; флаг можно повторять). Сервер слушает только
`127.0.0.1` и печатает адрес, браузер нужно открыть самостоятельно. Начать с объекта: поиск по
части имени (`ПрочиеРасходы`, `Заказ`), двойной клик по узлу раскрывает соседей.
Переключатель «Вид» показывает конфигурацию до и после расширений: `view=raw` (только база),
`view=effective` (с расширениями, заимствованный объект одним узлом) и `view=diff` (только связи,
которые добавили расширения); тот же параметр `view` принимает `object_graph`. Карта
открывается в effective, другой режим задаётся переключателем или параметром адреса `?view=raw`.

#### HTTP-связи между базами

Карта с несколькими `--project` показывает, какие объекты одной базы вызывают HTTP-сервисы
другой (кнопка «HTTP-связи», `GET /api/crosslinks`). Вызов `Новый HTTPСоединение(Сервер)` +
`Новый HTTPЗапрос(Путь)` сшивается с методом сервиса по пути
`/<публикация>/hs/<RootURL><шаблон>`, а сервер сопоставляется проекту маппингом хостов в
файле `<workspace>/.mcp1c/http-hosts.json`:

```json
{
  "version": 1,
  "hosts": [
    {"host": "erp.example.local", "project": "erp"},
    {"host": "*.shop.example.local", "project": "shop"}
  ]
}
```

`host`: имя сервера без схемы, порта и пути, без учёта регистра; `*.` в начале совпадает с
любым поддоменом. `project`: id проекта из реестра (поле `project` в `1c-project.json`).
Файла нет: все вызовы с литеральным сервером видны как «внешний HTTP». Сервер, которого нет
в маппинге, тоже внешний. Если сервер вычисляется (из настроек), сервис ищется по пути во
всех открытых проектах с меньшей достоверностью. Путь от `/hs/` при вычисляемом начале
(`СтруктураURI.ПутьНаСервере + "/hs/..."`, `СтрШаблон("/%1/hs/...")`, транспорт обмена БСП)
сшивается без сверки имени публикации. Путь, который вычисляется целиком, ребра не даёт:
бейдж `has-dynamic-http`; путь, известный частью, без совпадения, и неоткрытая база
мапленного хоста дают бейдж `has-unresolved-http`. Бейдж получают объекты, вызывающие
напрямую (без процедуры-хаба и не глубже `--graph-chain-depth`), иначе модуль вызова.
Файл читается на каждый запрос (не больше 1 МиБ), правка
маппинга не требует переиндексации. Две базы, зарегистрированные в одном workspace,
открываются как `--project /path/to/workspace#erp --project /path/to/workspace#shop`.
Агенту то же отдаёт `object_graph` с `crossProjects=[корни проектов]` или
`kinds=["http-call"]` (блок `httpLinks`).

## Коннектор живой базы

Исходники расширения `MCPКоннектор` лежат в [connector/src](connector/src), подробная
инструкция в [connector/README.md](connector/README.md). Кратко:

1. Загрузите `connector/src` в тестовую базу как расширение (конфигуратор,
   `/LoadConfigFromFiles <каталог> -Extension "MCPКоннектор"`) и при необходимости выгрузите
   `.cfe`. Версия формата XML зависит от версии платформы: если загрузка отвергает формат,
   пересоберите описание скриптом `connector/tools/build_src.py --from-dump <выгрузка вашей базы>`.
2. Опубликуйте HTTP-сервисы базы: веб-сервер на Windows или Linux, автономный сервер `ibsrv`
   (в том числе на macOS). Корневой URL сервиса `mcp-1c`.
3. Запустите сервер:

   ```sh
   MCP_1C_PASSWORD=... mcp1c --base http://<хост>/<база>/hs/mcp-1c --user <пользователь>
   ```

**Модель безопасности.**

- Коннектор только читает: метаданные, журнал регистрации, предопределённые элементы и
  результаты запросов. Эндпоинтов записи нет, `Выполнить()` и `Вычислить()` над входными
  данными не используются.
- `/query` выполняет только текст, который начинается со слова `ВЫБРАТЬ`/`SELECT`, остальное
  получает HTTP 403. Та же проверка продублирована на стороне сервера. `/validate-query`
  только разбирает запрос, не выполняя его.
- Привилегированный режим не включается: запросы идут с правами пользователя, под которым
  выполнена аутентификация (HTTP Basic), с учётом ограничений доступа на уровне записей.
  Заведите для коннектора отдельного пользователя с минимальными правами на чтение нужных
  объектов (и на журнал регистрации, если он нужен).
- Пароль передавайте через `MCP_1C_PASSWORD`, а не аргументом командной строки: аргументы
  попадают в историю оболочки и списки процессов. `list_bases` пароли не показывает.
- Ставьте коннектор на тестовые копии, а не на рабочую базу, и публикуйте сервис только в
  доверенной сети.

## Инструменты

Состав зависит от режима, профиля и наличия `--projects-root`. Колонка «core»: есть ли
инструмент в профиле `--tools=core`.

**Источник и навигация**

| Инструмент | Режим | core | Что делает |
|---|---|---|---|
| `server_info` | оба | да | версия, активный источник, проект и профиль |
| `set_dump`, `list_projects` | offline | да, нет | переключить выгрузку; найти выгрузки под корнем |
| `set_base`, `list_bases` | live | да | переключить базу; список настроенных баз |
| `get_configuration_info` | оба | нет | имя, версия, поставщик, число объектов по видам |
| `object_exists` | оба | да | есть ли объект, с похожими именами |
| `get_metadata_tree` | оба | да | объекты по видам с фильтрами `type` и `like` |
| `get_object_structure` | оба | да | реквизиты, табличные части, формы, команды объекта |
| `get_form_structure` | offline | да | элементы, реквизиты, команды и обработчики формы |
| `search_code` | offline | да | поиск по текстам модулей с именем охватывающей процедуры |

**Анализ перед изменением (offline)**

| Инструмент | core | Что делает |
|---|---|---|
| `context_pack` | да | структура, экспортный интерфейс модулей и использования объекта одним вызовом |

| `exchange_audit` | да | почему объект попадает или не попадает в обмен |

**Написание и проверка кода**

| Инструмент | Режим | core | Что делает |
|---|---|---|---|
| `get_query_schema` | offline | да | поля и виртуальные таблицы объекта для языка запросов |
| `bsl_syntax` | оба | да | синтаксис метода, свойства или типа платформы; `owner=<тип>` отдаёт все члены типа компактно, `query=Тип.Член` ищет среди членов типа, запрос по имени типа показывает его конструкторы (нужен индекс синтаксиса) |
| `validate_bsl` | offline | да | ссылки на несуществующие метаданные и неверное число аргументов; для своих процедур черновика возможные готовые методы БСП и конфигурации (подсказка по словам) |
| `query_advisor` | offline | да | анти-паттерны запроса с вариантами переписывания и подсказки по индексам |

**Живая база (live)**

| Инструмент | Что делает |
|---|---|
| `execute_query` | выполнить SELECT и вернуть строки |
| `validate_query`, `analyze_query` | проверить запрос без выполнения; найти тяжёлые конструкции |
| `get_event_log` | журнал регистрации с отбором по датам, уровню и пользователю |

| `data_health` | живой ли регистр или справочник: число записей, первая и последняя, прирост |

Все live-инструменты есть и в профиле `core`.

**Индексные (оба режима, только с `--projects-root`, все есть в `core`)**

| Инструмент | Что делает |
|---|---|
| `get_context_for_task` | минимальный достаточный контекст по описанию задачи в пределах бюджета символов |
| `index_status`, `reindex` | состояние индекса; регистрация проекта и пересборка |
| `find_symbol`, `get_symbol`, `get_module_structure` | поиск процедур и функций, точная сигнатура и тело, оглавление модуля |
| `find_api` | готовый метод программного интерфейса по описанию задачи: БСП этой выгрузки и сама конфигурация, двумя секциями; без запроса карта библиотеки и весь интерфейс модуля |
| `find_references`, `trace_call_graph`, `find_impact` | ссылки на символ, граф вызовов, что зависит от символа или объекта |
| `get_object`, `get_form_handlers` | объект из индекса с подписками, заданиями и правами; привязки обработчиков формы |
| `find_queries_using`, `find_register_writes` | запросы, читающие объект или поле; обращения к регистру |

Индексные инструменты понимают слои расширений (`view=effective`). Пределы каждого
инструмента описаны в [docs/tools-index.md](docs/tools-index.md).

Кроме инструментов, в offline-режиме сервер отдаёт prompts под типовые задачи
(`add-attribute`, `new-object`, `why-invisible`, `not-in-exchange`, `change-posting`) и
ресурсы `onec://metadata`, `onec://object/{type}/{name}`, `onec://standards/naming`,
`onec://query-lang/cheatsheet` с автодополнением имён метаданных.

## Ограничения

- **Время и память индексации.** Холодный полный индекс крупной типовой конфигурации (около
  49 тыс. файлов) строится около 4 минут, пиковая память процесса около 6 ГиБ, файл индекса
  около 2,2 ГиБ. Замеры в [docs/benchmarks.md](docs/benchmarks.md).
- **Инкрементальный `reindex` на конфигурациях около 50 тыс. файлов** сейчас падает на лимите
  числа параметров SQLite. Обходной путь: `reindex mode=full`.
- **`search_code` читает выгрузку напрямую**, полнотекстовый индекс пока не используется.
- **Полнота индекса.** Тексты запросов, собранные динамически, в индекс не попадают;
  `find_impact` обходит не все виды связей; объединённый вид с расширениями
  (`view=effective`) не сливает формы расширений. Подробности в
  [docs/tools-index.md](docs/tools-index.md).
- **Live-режим** не даёт структуру форм и поиск по коду (их нет во время исполнения) и
  проверен меньше, чем offline.
- **macOS.** Клиентская платформа для macOS не публикует базу через веб-сервер: для
  live-режима нужен автономный сервер `ibsrv` или публикация на Windows или Linux.
- **Windows.** `server_info` не показывает потребление памяти процесса.
- **Индекс синтаксиса** нужно собрать самостоятельно, для этого нужна установленная платформа.
- `mcp1c graph` не открывает браузер сам, только печатает адрес.
- **HTTP-связи.** Адрес выводится только внутри метода: соединение или запрос, пришедшие
  параметром, дают бейдж на модуле вызова, а не ребро. Сервер из настроек ищет сервис по
  пути во всех открытых базах. Радиус и god-node HTTP-связей не видят: это отдельный слой.

Открытые направления перечислены в [ROADMAP.md](ROADMAP.md).

## Разработка и тесты

```sh
go build ./...
go vet ./...
go test ./...                     # без реальной выгрузки и без индекса синтаксиса
go test -race ./...
CGO_ENABLED=0 GOOS=windows GOARCH=amd64 go build ./...
```

Тесты на реальных данных включаются переменными окружения и без них пропускаются:

| Переменная | Назначение |
|---|---|
| `ONEC_DUMP` (или `MCP1C_SPIKE_DUMP`) | корень реальной XML-выгрузки для тестов индекса, резолвера и `get_context_for_task` |
| `MCP_1C_SYNTAX_INDEX` | настоящий индекс синтаксиса для тех же тестов |
| `ONEC_POSTING_INTERCEPTS`, `ONEC_POSTING_NOBASE` | пары «документ и перехватчик» для тестов проведения под расширениями |
| `ONEC_REAL_DUMP`, `ONEC_REAL_FORM`, `ONEC_REAL_OBJECT`, `ONEC_FIND`, `ONEC_HBK` | тесты offline-слоя на реальных данных |
| `MCP_1C_BASE_URL`, `MCP_1C_USER`, `MCP_1C_PASSWORD` | интеграционные тесты коннектора на живой базе |

Real-dump тесты запускайте по одному пакету (`-run`): каждый пакет строит полный индекс
выгрузки, и параллельный прогон упирается в стандартный таймаут `go test`.

Устройство кода: [CLAUDE.md](CLAUDE.md) (карта пакетов и правила для ИИ-агентов),
[docs/architecture-index.md](docs/architecture-index.md), решения в [docs/adr](docs/adr).
Как предложить изменение: [CONTRIBUTING.md](CONTRIBUTING.md). Уязвимости:
[SECURITY.md](SECURITY.md).

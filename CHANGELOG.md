## [Не выпущено]

### Добавлено

- `query_advisor`: десять правил из стандартов разработки 1С, у каждого номер стандарта в
  тексте предупреждения. `SumAsCount` (#std787: подсчёт строк через `СУММА(1)` и условный счёт
  без `ВЫРАЗИТЬ`), `NestedJoin` (#std655: второе соединение стоит до условия `ПО` первого),
  `FullOuterJoin` (#std435), `UnionWithoutAll` (#std434), `OrAcrossFields` (#std658: `ИЛИ` по
  разным полям на верхнем уровне `ГДЕ`), `FunctionOnFilterField` (#std658: функция даты или
  `ПОДСТРОКА` с первого символа над полем, сравниваемым с параметром или литералом),
  `CompositeDereference` (#std654: `Регистратор.Поле`), `TopWithAutoOrder` (#std412),
  `VirtualTableComplexParams` (#std657: подзапрос с соединением или обращение через точку в
  параметрах виртуальной таблицы), `VirtualTableFilterInWhere` (#std657: измерение виртуальной
  таблицы сравнивается с параметром в `ГДЕ`, хотя параметры у таблицы есть; нужны метаданные,
  только offline). Первые девять работают и в live-режиме (`analyze_query`). Правила читают
  текст без комментариев и без содержимого строковых литералов.
  Замер на 20 892 запросах типовой конфигурации, доля запросов со срабатыванием:
  `OrAcrossFields` 1,27%, `VirtualTableComplexParams` 1,24%, `NestedJoin` 1,20%,
  `UnionWithoutAll` 1,18%, `SumAsCount` 0,73%, `FullOuterJoin` 0,40%,
  `FunctionOnFilterField` 0,18%, `VirtualTableFilterInWhere` 0,05%, `CompositeDereference`
  0,05%, `TopWithAutoOrder` 0,01%. Замер повторяет `TestRealDumpAdvisorRuleFrequency`
  (`ONEC_REAL_DUMP`), он же падает, если правило из стандартов срабатывает чаще чем на 10%
  запросов.
  Границы: составной тип распознаётся только у поля `Регистратор` и только при обращении через
  псевдоним таблицы (`Т.Регистратор.Дата`); правила читают русские ключевые слова, английские
  (`SELECT`, `WHERE`, `JOIN`) не распознаются; `ИЛИ` целиком в скобках, по
  полям без псевдонима и в условии `ПО` не проверяется; отбор измерения в `ГДЕ` ловится только
  при сравнении с параметром. Не сделаны правилами: `СрезПоследних` с датой (#std708, так
  штатно читают значение на дату документа, по тексту ошибку от замысла не отличить) и
  сортировка по полю, где возможен `NULL` (#std412, нужна обнуляемость поля).

- `find_api`: поиск готового метода программного интерфейса по описанию задачи среди
  экспортных методов общих модулей и модулей менеджеров. Выдача двумя секциями (БСП этой
  выгрузки с её версией и сама конфигурация): выражение вызова, сигнатура со значениями по
  умолчанию, первая строка описания, контекст исполнения, пометка устаревшего; за десятью
  полными описаниями идёт короткий список следующих десяти методов. Поиск идёт по имени
  метода, имени модуля и полному комментарию, словоформы запроса сводятся с именем метода
  («удаление» находит `Удалить`), редкое слово запроса весит больше частых. На эталоне
  (одна конфигурация, запросы отобраны проверкой) нужный метод виден агенту у 94% запросов
  всего набора, вызов занимает миллисекунды.
- `find_api`: вход `query` стал необязательным, добавлен вход `module`. Вызов без
  `query` больше не ошибка `invalid_argument`: без аргументов отдаёт карту библиотеки (подсистемы БСП и их
  модули с числом методов), с `module` весь программный интерфейс модуля одной строкой на
  метод, с `module` и `query` ищет внутри модуля.
- Карточки задач для `find_api`: формулировки задачи словами разработчика по каждому методу
  программного интерфейса, написанные языковой моделью один раз на версию библиотеки или
  конфигурации (`cmd/apicards`). Сервер читает наборы из каталога
  `<каталог настроек пользователя>/mcp1c/api-cards` (флаг `--api-cards`, переменная
  `MCP_1C_API_CARDS`, `none` отключает). На эталоне с карточками нужный метод виден агенту
  у 98% запросов против 94% и стоит первым в своей секции у 65% против 51%; запросы эталона
  и карточки писала одна модель, на живых запросах прирост может быть меньше. Сами наборы в
  репозиторий не входят: без них сервер ищет по имени и комментарию.
- `find_api`: в описании метода тип возвращаемого значения из комментария (`returns`), число
  вызовов из других модулей (`calls`) и оператор одного настоящего вызова (`example`); входы
  `returns` и `accepts` отбирают методы по типу результата и по типу параметра (без `query`
  и `module` дают `invalid_argument`). Вызов стал дороже: медиана 23 мс против 5.
- Ходовые методы библиотеки: `get_context_for_task` отдаёт поле `coreMethods`, а `find_api`
  без аргументов поле `core`: до ста методов БСП, которыми пользуется больше всего прикладных
  объектов этой конфигурации (только имена, по модулям). Список считается по индексу базы; на
  УТ 11.5 он закрывает 82% вызовов действующих методов программного интерфейса библиотеки из
  прикладного кода (без обработчиков событий). Тот же список отдаёт `server_info` (поле
  `coreMethods`): в журналах автора из 17 сессий с сервером `server_info` встретился в 15, а
  `get_context_for_task` в 5. Список считается в фоне с запуска сервера, сам `server_info` не
  ждёт: пока списка нет, отдаёт `coreNote` (считается или почему не посчитан). Цена: сервер в
  каждой сессии открывает активный проект и строит индекс слов в фоне, даже если индексные
  инструменты не понадобятся. Снимок списка для хука пишется в каталог кэша пользователя
  (флаг `--core-snapshot`, `none` отключает).
- Хук `tools/hooks/bsl_ready_methods.py` на первом за сессию обращении к `.bsl` кладёт в
  контекст агента ходовые методы БСП: сервер оставляет их снимком в каталоге кэша
  пользователя (`mcp1c/core`). Рекомендуемый matcher хука теперь
  `Read|Write|Edit|MultiEdit`.
- `get_symbol` отдаёт полный комментарий метода полем `doc`.
- `validate_bsl`: поля `readyMethods` и `readyMethodsNote`, вход `module`. Для процедур и
  функций, объявленных в черновике (кроме обработчиков событий и перехватчиков), называются
  возможные готовые методы БСП и конфигурации по словам имени и комментария. Это подсказка,
  а не находка: в `count` и `findings` она не входит, большинство названного к процедуре не
  относится. На замере готовый метод, который функция повторяет, назван у 69% функций (75% с
  карточками задач); на функциях, которые ничего не повторяют, кандидаты названы у 78-82%.
- `get_context_for_task`: поле `readyMethods`, до восьми готовых методов, у которых не меньше
  двух слов задачи стоят в имени, модуле или описании (вне бюджета символов; не собирается
  для вопросов о правах и обмене; качество блока не мерялось).
- `tools/hooks/bsl_ready_methods.py`: хук Claude Code, который после записи `.bsl` с новыми
  процедурами напоминает агенту проверить их через `validate_bsl`.
- `evals/findapi`: эталон качества `find_api`, 498 пар «задача словами → готовый метод»,
  построенных из реальных вызовов методов в коде УТ 11.5 (имя метода скрыто, запрос и его
  пересказ пишет модель, пару принимают две независимые проверяющие), и счётчик со
  сравнением с базой. Описание, база и ограничения: `docs/find-api-eval.md`.

### Изменено

- `query_advisor`: граница слова перед ключевым словом определяется по целому символу. Раньше
  слово находилось в хвосте кириллического идентификатора (`ИЛИ` в `Оплатили`, `ПО` в
  `СкладПО`): проверялся последний байт предыдущей буквы, а не сама буква. На замере по
  типовой конфигурации изменилось одно прежнее правило: `NonLeadingDimensionFilter`
  срабатывает на 1267 запросах вместо 1183 (имя измерения больше не засчитывается как отбор,
  когда оно лишь хвост другого имени в параметрах виртуальной таблицы); остальные прежние
  правила дают те же числа.
- `query_advisor`: поиск ключевых слов больше не переводит текст в верхний регистр. Символ,
  который в верхнем регистре занимает больше байт, сдвигал смещения, и разбор такого текста мог
  завершиться паникой.
- Индекс хранит у символа путь областей, первую строку описания и полный комментарий.
  Схема индекса 8: каждый индекс после обновления сервера один раз пересобирается
  полностью.
- `get_module_structure` отдаёт области модуля, предупреждение `regions_not_indexed` убрано.

## [0.1.0]

Первый публичный выпуск.

### Добавлено

- MCP-сервер `mcp1c` (stdio, MCP 2025-06-18), один статический бинарник без cgo для Windows,
  macOS и Linux (amd64, arm64).
- Offline-режим по XML-выгрузке конфигурации: навигация по метаданным, структура объектов и
  форм, поиск по коду, схема объектов для языка запросов, разбор записи и проведения,
  права и RLS, видимость, обмены, чеклист нового объекта, влияние на формы, точки
  расширения БСП, анализ расширений, сравнение выгрузок, проверка написанного кода
  (`validate_bsl`, `query_advisor`).
- Персистентный SQLite-индекс проекта (`--projects-root`, манифест `1c-project.json`):
  символы, ссылки, граф вызовов, метаданные, запросы, обращения к регистрам, привязки форм,
  объектный граф, слои расширений, инкрементальное обновление и
  `get_context_for_task` для минимального контекста по описанию задачи.
- Live-режим через расширение-коннектор `MCPКоннектор` с HTTP-сервисом только для чтения:
  SELECT-запросы, проверка запросов, журнал регистрации, предопределённые элементы,
  подсистемы, живость данных, профили и диагностика доступа, сверка базы с выгрузкой,
  несколько баз с явным выбором.
- Профили инструментов `--tools=full|core`, инструкции для агента, собранные из
  фактически зарегистрированных инструментов, prompts под типовые задачи и ресурсы.
- `syntaxgen`: сборка индекса синтаксиса из файлов справки установленной платформы.
- `bsl_syntax` как справочник по API платформы: вход `owner` ограничивает поиск членами типа,
  а без `query` отдаёт все члены типа в компактной форме (конструкторы, методы, свойства,
  события; лимит 150 с `truncated`/`total`); форма `query=Тип.Член`; запрос по имени типа
  возвращает поле `type` с числом членов и конструкторами. Прежние вызовы отвечают как раньше.
- `mcp1c graph`: локальная веб-карта объектного графа.
